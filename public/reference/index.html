A.1

Filtering & Sorting

Filter products to one category within a price range, then sort and limit — the most basic interview warm-up, but a useful place to anchor the syntax differences.

SQL
-- Step 1: sample table
CREATE TABLE products (
    product_id  INT,
    name        VARCHAR(50),
    category    VARCHAR(30),
    price       DECIMAL(10,2)
);

INSERT INTO products VALUES
(1, 'Laptop',       'Electronics', 899.00),
(2, 'Headphones',   'Electronics', 149.00),
(3, 'Desk Lamp',    'Home',        35.00),
(4, 'Monitor',      'Electronics', 310.00),
(5, 'Office Chair', 'Home',        220.00),
(6, 'Tablet',       'Electronics', 480.00);

-- Step 2: filter then sort
SELECT product_id, name, category, price
FROM products
WHERE category = 'Electronics'        -- only this category
  AND price BETWEEN 100 AND 500       -- inclusive price range
ORDER BY price DESC                   -- most expensive first
LIMIT 3;                              -- only the top 3 rows
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("FilterSort").getOrCreate()

data = [
    (1, "Laptop",       "Electronics", 899.00),
    (2, "Headphones",   "Electronics", 149.00),
    (3, "Desk Lamp",     "Home",       35.00),
    (4, "Monitor",      "Electronics", 310.00),
    (5, "Office Chair", "Home",        220.00),
    (6, "Tablet",       "Electronics", 480.00),
]
df = spark.createDataFrame(data, ["product_id", "name", "category", "price"])

result = (
    df.filter(F.col("category") == "Electronics")  # keep only Electronics rows
      .filter(F.col("price").between(100, 500))     # price range filter
      .orderBy(F.col("price").desc())                 # most expensive first
      .limit(3)                                        # top 3 rows only
)

result.show()
PYPython
import pandas as pd

data = {
    "product_id": [1, 2, 3, 4, 5, 6],
    "name":       ["Laptop", "Headphones", "Desk Lamp", "Monitor", "Office Chair", "Tablet"],
    "category":   ["Electronics", "Electronics", "Home", "Electronics", "Home", "Electronics"],
    "price":      [899.00, 149.00, 35.00, 310.00, 220.00, 480.00],
}
df = pd.DataFrame(data)

result = (
    df[(df["category"] == "Electronics") &      # boolean mask: category match
       (df["price"].between(100, 500))]          # AND price in range
      .sort_values("price", ascending=False)       # most expensive first
      .head(3)                                       # top 3 rows
)

print(result)
Interview angle: all three look trivial here, but the follow-up is usually "what happens under the hood?" — SQL and Spark push the filter down before scanning (predicate pushdown), while pandas always loads the full DataFrame into memory first and filters after. That difference is exactly why the same-looking code scales very differently.

Aggregation & HAVING

Total sales per region, keeping only regions above a threshold — the question that tests whether you understand WHERE runs before grouping and HAVING runs after.

SQL
CREATE TABLE sales (sale_id INT, region VARCHAR(20), amount DECIMAL(10,2));

INSERT INTO sales VALUES
(1,'West', 4000),(2,'West', 7000),(3,'East', 3000),
(4,'East', 2000),(5,'North',12000),(6,'North', 9000),
(7,'South', 1500),(8,'South', 1200);

SELECT
    region,
    SUM(amount) AS total_sales       -- aggregate per group
FROM sales
GROUP BY region                      -- one row per region
HAVING SUM(amount) > 10000;          -- filters the AGGREGATE result, not raw rows
-- WHERE can't reference SUM() here because WHERE runs before grouping;
-- HAVING exists specifically to filter after aggregation.
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("AggHaving").getOrCreate()

data = [
    (1,"West",4000),(2,"West",7000),(3,"East",3000),
    (4,"East",2000),(5,"North",12000),(6,"North",9000),
    (7,"South",1500),(8,"South",1200),
]
df = spark.createDataFrame(data, ["sale_id", "region", "amount"])

result = (
    df.groupBy("region")                            # one group per region
      .agg(F.sum("amount").alias("total_sales"))      # SUM aggregate, same as SQL
      .filter(F.col("total_sales") > 10000)            # HAVING equivalent: filter AFTER aggregating
)

result.show()
PYPython
import pandas as pd

data = {
    "sale_id": [1,2,3,4,5,6,7,8],
    "region":  ["West","West","East","East","North","North","South","South"],
    "amount":  [4000,7000,3000,2000,12000,9000,1500,1200],
}
df = pd.DataFrame(data)

totals = df.groupby("region")["amount"].sum().reset_index(name="total_sales")  # aggregate per group

result = totals[totals["total_sales"] > 10000]   # HAVING equivalent: filter the aggregated frame

print(result)
Interview angle: the WHERE-before / HAVING-after distinction maps onto all three: filter the raw rows before grouping by chaining a .filter() before .groupBy() (or a pandas boolean mask before .groupby()), and filter the aggregate by applying the condition after the aggregation step, exactly as shown.
A.3

All Join Types

Inner, left, and anti joins between customers and orders — anti join (customers with zero orders) is the one candidates most often fumble.

SQL
CREATE TABLE customers (customer_id INT, name VARCHAR(50));
CREATE TABLE orders (order_id INT, customer_id INT, amount INT);

INSERT INTO customers VALUES (1,'Alice'),(2,'Bob'),(3,'Cleo');
INSERT INTO orders VALUES (101,1,250),(102,1,90),(103,2,400);
-- Note: Cleo (customer_id 3) has placed no orders

-- INNER JOIN: only customers that have at least one matching order
SELECT c.customer_id, c.name, o.order_id, o.amount
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- LEFT JOIN: every customer, with NULLs where no order exists
SELECT c.customer_id, c.name, o.order_id, o.amount
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- ANTI JOIN idiom: customers with NO orders at all
-- (standard ANSI SQL has no ANTI JOIN keyword — this NULL-check pattern is the workaround)
SELECT c.customer_id, c.name
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;       -- keep only rows where the join found no match
PySpark
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("Joins").getOrCreate()

customers = spark.createDataFrame([(1,"Alice"),(2,"Bob"),(3,"Cleo")], ["customer_id","name"])
orders    = spark.createDataFrame([(101,1,250),(102,1,90),(103,2,400)], ["order_id","customer_id","amount"])

# INNER JOIN — default join type when "how" is omitted
inner = customers.join(orders, on="customer_id", how="inner")
inner.show()

# LEFT JOIN — keep every customer row, NULLs where no order matches
left = customers.join(orders, on="customer_id", how="left")
left.show()

# LEFT ANTI JOIN — Spark has this as a first-class join type, no NULL-filter trick needed
no_orders = customers.join(orders, on="customer_id", how="left_anti")
no_orders.show()
PYPython
import pandas as pd

customers = pd.DataFrame({"customer_id":[1,2,3], "name":["Alice","Bob","Cleo"]})
orders    = pd.DataFrame({"order_id":[101,102,103], "customer_id":[1,1,2], "amount":[250,90,400]})

# INNER JOIN — pandas calls it "merge"; how="inner" is the default
inner = customers.merge(orders, on="customer_id", how="inner")
print(inner)

# LEFT JOIN — every customer kept, NaN where no order matches
left = customers.merge(orders, on="customer_id", how="left")
print(left)

# ANTI JOIN equivalent — pandas has no how="anti"; filter the left-merge result for unmatched rows
no_orders = left[left["order_id"].isna()][["customer_id", "name"]]
print(no_orders)
Interview angle: Spark exposes left_anti and left_semi as real join strategies because it can plan them more efficiently than a join-then-filter; pandas has neither, so you reach for a left merge plus an isna() mask. Knowing pandas lacks this is itself a good answer if asked directly.
A.4

Window Functions — Ranking

ROW_NUMBER vs RANK vs DENSE_RANK on tied scores — the differences only show up when there are ties, which is exactly why interviewers pick a dataset with ties.

SQL
CREATE TABLE scores (name VARCHAR(20), score INT);
INSERT INTO scores VALUES ('Ana',90),('Ben',90),('Cid',85),('Dee',85),('Eli',70);

SELECT
    name, score,
    ROW_NUMBER() OVER (ORDER BY score DESC) AS row_num,      -- always unique, no ties: 1,2,3,4,5
    RANK()       OVER (ORDER BY score DESC) AS rank_,         -- ties share a rank, then SKIPS: 1,1,3,3,5
    DENSE_RANK() OVER (ORDER BY score DESC) AS dense_rank_    -- ties share a rank, NO gap after: 1,1,2,2,3
FROM scores;
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder.appName("Ranking").getOrCreate()

data = [("Ana",90),("Ben",90),("Cid",85),("Dee",85),("Eli",70)]
df = spark.createDataFrame(data, ["name","score"])

w = Window.orderBy(F.col("score").desc())   # single global ranking — no partitionBy needed here

result = (
    df.withColumn("row_num", F.row_number().over(w))      # unique sequential number, ties broken arbitrarily
      .withColumn("rank_", F.rank().over(w))                # ties tie, next rank skips ahead
      .withColumn("dense_rank_", F.dense_rank().over(w))     # ties tie, next rank stays consecutive
)
result.show()
PYPython
import pandas as pd

df = pd.DataFrame({"name":["Ana","Ben","Cid","Dee","Eli"], "score":[90,90,85,85,70]})

df["row_num"]     = df["score"].rank(method="first", ascending=False)  # unique, by row order
df["rank_"]       = df["score"].rank(method="min",   ascending=False)  # ties share lowest rank (gaps)
df["dense_rank_"] = df["score"].rank(method="dense",  ascending=False) # ties share rank (no gaps)

print(df)
Interview angle: walk through the tie explicitly — Ana and Ben both score 90. ROW_NUMBER arbitrarily picks one of them for rank 1 and the other for rank 2; RANK gives both rank 1 and then jumps straight to rank 3 for the next distinct score; DENSE_RANK gives both rank 1 and the next distinct score becomes rank 2. That's the entire question — everything else is syntax.
A.5

Running Totals & Moving Averages

A cumulative sum and a trailing 3-day average over daily sales — frame clauses (ROWS BETWEEN) are the part people forget under pressure.

SQL
CREATE TABLE daily_sales (sale_date DATE, amount INT);
INSERT INTO daily_sales VALUES
('2024-01-01',100),('2024-01-02',150),('2024-01-03',90),
('2024-01-04',200),('2024-01-05',120);

SELECT
    sale_date, amount,
    SUM(amount) OVER (
        ORDER BY sale_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW   -- everything from the start through this row
    ) AS running_total,
    AVG(amount) OVER (
        ORDER BY sale_date
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW            -- this row + the 2 before it = 3-day window
    ) AS moving_avg_3d
FROM daily_sales;
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder.appName("RunningTotal").getOrCreate()

data = [("2024-01-01",100),("2024-01-02",150),("2024-01-03",90),
        ("2024-01-04",200),("2024-01-05",120)]
df = spark.createDataFrame(data, ["sale_date","amount"])
df = df.withColumn("sale_date", F.to_date("sale_date"))   # cast string -> date type

running_window = (
    Window.orderBy("sale_date")
          .rowsBetween(Window.unboundedPreceding, Window.currentRow)  # start through current row
)
moving_window = (
    Window.orderBy("sale_date")
          .rowsBetween(-2, Window.currentRow)   # 2 rows back + current row = 3-day window
)

result = (
    df.withColumn("running_total", F.sum("amount").over(running_window))
      .withColumn("moving_avg_3d", F.avg("amount").over(moving_window))
)
result.show()
PYPython
import pandas as pd

df = pd.DataFrame({
    "sale_date": pd.to_datetime(["2024-01-01","2024-01-02","2024-01-03","2024-01-04","2024-01-05"]),
    "amount":    [100,150,90,200,120],
}).sort_values("sale_date")

df["running_total"] = df["amount"].cumsum()                                   # cumulative sum down the column
df["moving_avg_3d"]  = df["amount"].rolling(window=3, min_periods=1).mean()    # trailing 3-row average

print(df)
Interview angle: min_periods=1 in the pandas rolling call matters — without it, the first two rows (which don't yet have 3 prior rows) would return NaN, whereas SQL and Spark's frame clauses naturally shrink the window at the start of the data and still return a value. That edge-case awareness is what separates a working answer from a technically-correct-but-buggy one.

Top-N Per Group

Find the 2 highest-paid employees in each department — one of the most frequently asked window-function questions in DE screens.

SQL
-- Step 1: create the table structure
CREATE TABLE employees (
    emp_id      INT,            -- unique identifier for each employee
    name        VARCHAR(50),    -- employee full name
    department  VARCHAR(50),    -- department the employee belongs to
    salary      INT             -- monthly salary in USD
);

-- Step 2: load sample rows
INSERT INTO employees VALUES
(1, 'Alice',   'Engineering', 9000),
(2, 'Bob',     'Engineering', 8500),
(3, 'Charlie', 'Engineering', 7000),
(4, 'Diana',   'Sales',       6000),
(5, 'Evan',    'Sales',       6500),
(6, 'Farah',   'Sales',       5800),
(7, 'Gabe',    'Marketing',   7200);

-- Step 3: rank employees within each department, then keep top 2
SELECT emp_id, name, department, salary
FROM (
    SELECT
        emp_id, name, department, salary,
        ROW_NUMBER() OVER (          -- assigns 1, 2, 3... per partition
            PARTITION BY department  -- restart counting for each department
            ORDER BY salary DESC     -- rank 1 = highest salary first
        ) AS salary_rank
    FROM employees
) ranked
WHERE salary_rank <= 2;              -- keep only ranks 1 and 2 → "top 2"
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder.appName("TopNPerGroup").getOrCreate()

data = [
    (1, "Alice",   "Engineering", 9000),
    (2, "Bob",     "Engineering", 8500),
    (3, "Charlie", "Engineering", 7000),
    (4, "Diana",   "Sales",       6000),
    (5, "Evan",    "Sales",       6500),
    (6, "Farah",   "Sales",       5800),
    (7, "Gabe",    "Marketing",   7200),
]
columns = ["emp_id", "name", "department", "salary"]
df = spark.createDataFrame(data, columns)

window_spec = (
    Window.partitionBy("department")        # restart numbering per department
          .orderBy(F.col("salary").desc())  # highest salary ranked first
)

ranked_df = df.withColumn("salary_rank", F.row_number().over(window_spec))

top_2_per_dept = ranked_df.filter(F.col("salary_rank") <= 2)

top_2_per_dept.select("emp_id", "name", "department", "salary").show()
PYPython
import pandas as pd

data = {
    "emp_id":     [1, 2, 3, 4, 5, 6, 7],
    "name":       ["Alice", "Bob", "Charlie", "Diana", "Evan", "Farah", "Gabe"],
    "department": ["Engineering", "Engineering", "Engineering",
                    "Sales", "Sales", "Sales", "Marketing"],
    "salary":     [9000, 8500, 7000, 6000, 6500, 5800, 7200],
}
df = pd.DataFrame(data)

    df.groupby("department")["salary"]

top_2_per_dept = df[df["salary_rank"] <= 2]

print(top_2_per_dept[["emp_id", "name", "department", "salary"]])
Interview angle: SQL and pandas both reach for a ranking function, but PySpark makes the partition logic an explicit object (Window) because the computation has to be planned and distributed before it runs — the natural follow-up is "what happens differently at scale?"
A.7

Set Operations

UNION, UNION ALL, INTERSECT, and EXCEPT across two email lists — testing whether you know which one dedupes and which one doesn't.

SQL
CREATE TABLE campaign_a (email VARCHAR(50));
CREATE TABLE campaign_b (email VARCHAR(50));

INSERT INTO campaign_a VALUES ('amy@mail.com'),('ben@mail.com'),('cleo@mail.com');
INSERT INTO campaign_b VALUES ('ben@mail.com'),('cleo@mail.com'),('drew@mail.com');

-- UNION: combine and remove duplicate rows
SELECT email FROM campaign_a
UNION
SELECT email FROM campaign_b;

-- UNION ALL: combine and KEEP duplicates (faster — skips the dedup step)
SELECT email FROM campaign_a
UNION ALL
SELECT email FROM campaign_b;

-- INTERSECT: emails present in BOTH campaigns
SELECT email FROM campaign_a
INTERSECT
SELECT email FROM campaign_b;

-- EXCEPT: emails in campaign_a that are NOT in campaign_b
SELECT email FROM campaign_a
EXCEPT
SELECT email FROM campaign_b;
PySpark
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("SetOps").getOrCreate()

campaign_a = spark.createDataFrame([("amy@mail.com",),("ben@mail.com",),("cleo@mail.com",)], ["email"])
campaign_b = spark.createDataFrame([("ben@mail.com",),("cleo@mail.com",),("drew@mail.com",)], ["email"])

campaign_a.union(campaign_b).distinct().show()   # UNION: combine + dedupe
campaign_a.union(campaign_b).show()               # UNION ALL: combine, keep duplicates
campaign_a.intersect(campaign_b).show()           # INTERSECT: rows present in both
campaign_a.subtract(campaign_b).show()            # EXCEPT: in A but not in B (deduped, matches SQL EXCEPT)
PYPython
import pandas as pd

campaign_a = pd.DataFrame({"email": ["amy@mail.com","ben@mail.com","cleo@mail.com"]})
campaign_b = pd.DataFrame({"email": ["ben@mail.com","cleo@mail.com","drew@mail.com"]})

union     = pd.concat([campaign_a, campaign_b]).drop_duplicates()                          # UNION
union_all = pd.concat([campaign_a, campaign_b])                                              # UNION ALL
intersect = campaign_a[campaign_a["email"].isin(campaign_b["email"])].drop_duplicates()       # INTERSECT
except_   = campaign_a[~campaign_a["email"].isin(campaign_b["email"])].drop_duplicates()      # EXCEPT

print(union); print(intersect); print(except_)
Interview angle: pandas has no native set-operation methods — isin() plus a boolean mask is the idiom for INTERSECT/EXCEPT, and concat() plus drop_duplicates() stands in for UNION. Saying that plainly is a better answer than trying to force a method that doesn't exist.

B.1

Deduplication

Customer records have duplicate emails from repeated syncs — keep only the most recently updated row per email. A core data-quality pattern, not just a syntax trick.

SQL
CREATE TABLE customers (
    customer_id INT,
    email       VARCHAR(100),
    updated_at  TIMESTAMP        -- tells us which copy is the freshest
);

INSERT INTO customers VALUES
(1, 'amy@mail.com',  '2024-01-10'),
(2, 'amy@mail.com',  '2024-03-22'),  -- duplicate email, newer timestamp
(3, 'ben@mail.com',  '2024-02-05'),
(4, 'cleo@mail.com', '2024-01-01'),
(5, 'cleo@mail.com', '2023-12-15'); -- duplicate email, older timestamp

SELECT customer_id, email, updated_at
FROM (
    SELECT
        customer_id, email, updated_at,
        ROW_NUMBER() OVER (
            PARTITION BY email           -- group duplicate rows together
            ORDER BY updated_at DESC     -- most recent row becomes rank 1
        ) AS recency_rank
    FROM customers
) deduped
WHERE recency_rank = 1;                  -- one surviving row per email
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder.appName("Dedup").getOrCreate()

data = [
    (1, "amy@mail.com",  "2024-01-10"),
    (2, "amy@mail.com",  "2024-03-22"),
    (3, "ben@mail.com",  "2024-02-05"),
    (4, "cleo@mail.com", "2024-01-01"),
    (5, "cleo@mail.com", "2023-12-15"),
]
df = spark.createDataFrame(data, ["customer_id", "email", "updated_at"])
df = df.withColumn("updated_at", F.to_date("updated_at"))   # cast string -> date

window_spec = Window.partitionBy("email").orderBy(F.col("updated_at").desc())
ranked_df = df.withColumn("recency_rank", F.row_number().over(window_spec))

deduped_df = ranked_df.filter(F.col("recency_rank") == 1).drop("recency_rank")
deduped_df.show()

# Note: dropDuplicates("email") is shorter but does NOT guarantee which
# duplicate survives — the window approach above is what interviewers
# expect when "most recent" specifically matters.
PYPython
import pandas as pd

data = {
    "customer_id": [1, 2, 3, 4, 5],
    "email":       ["amy@mail.com", "amy@mail.com", "ben@mail.com",
                     "cleo@mail.com", "cleo@mail.com"],
    "updated_at":  ["2024-01-10", "2024-03-22", "2024-02-05",
                     "2024-01-01", "2023-12-15"],
}
df = pd.DataFrame(data)
df["updated_at"] = pd.to_datetime(df["updated_at"])   # string -> real datetime

df_sorted = df.sort_values("updated_at", ascending=False)   # most recent row per email first

# drop_duplicates keeps the FIRST occurrence per key by default — since we
# sorted by recency first, "first" now effectively means "most recent"
deduped_df = df_sorted.drop_duplicates(subset="email", keep="first")
deduped_df = deduped_df.sort_values("customer_id").reset_index(drop=True)

print(deduped_df)
Interview angle: a common wrong answer jumps straight to DISTINCT or drop_duplicates() with no tiebreaker — that only works if duplicate rows are truly identical. The moment "most recent" or "highest priority" enters the question, you need an explicit ordering rule before deduping.
B.2

Null Handling

Missing bonus values and missing managers — defaulting nulls, distinguishing "zero" from "unknown", and filtering for nulls correctly.

SQL
CREATE TABLE employees (emp_id INT, name VARCHAR(30), bonus INT, manager_id INT);
INSERT INTO employees VALUES
(1,'Alice', 500, NULL),    -- top of the hierarchy: no manager
(2,'Bob',   NULL, 1),      -- bonus not yet assigned
(3,'Cleo',  0,    1);      -- bonus genuinely zero, NOT missing

-- COALESCE: substitute a default only where the value is actually NULL
SELECT emp_id, name, COALESCE(bonus, 0) AS bonus_filled
FROM employees;
-- Cleo's real 0 is untouched; only Bob's NULL becomes 0 — this distinction matters

-- IS NULL / IS NOT NULL: the only correct way to test for NULL
-- ("bonus = NULL" is always unknown/false in SQL, never matches anything)
SELECT emp_id, name FROM employees WHERE manager_id IS NULL;       -- top of hierarchy
SELECT emp_id, name FROM employees WHERE bonus IS NOT NULL;         -- bonus already assigned

-- NULLIF: the inverse of COALESCE — turn a sentinel value INTO null
SELECT emp_id, NULLIF(bonus, 0) AS bonus_or_null FROM employees;    -- Cleo's 0 becomes NULL here
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("Nulls").getOrCreate()

data = [(1,"Alice",500,None), (2,"Bob",None,1), (3,"Cleo",0,1)]
df = spark.createDataFrame(data, ["emp_id","name","bonus","manager_id"])

# coalesce: substitute a default only where the value is actually null
df.withColumn("bonus_filled", F.coalesce(F.col("bonus"), F.lit(0))).show()

# isNull / isNotNull: the correct null tests (== None does not work in Spark either)
df.filter(F.col("manager_id").isNull()).show()      # top of hierarchy
df.filter(F.col("bonus").isNotNull()).show()         # bonus already assigned

# the inverse: turn a sentinel value (0) into an actual null
df.withColumn("bonus_or_null",
              F.when(F.col("bonus") == 0, None).otherwise(F.col("bonus"))).show()
PYPython
import pandas as pd
import numpy as np

data = {

Pivot / Unpivot

Reshape quarterly sales from long format (one row per region/quarter) to wide format (one column per quarter), and back again.

SQL
CREATE TABLE sales_long (region VARCHAR(20), quarter VARCHAR(2), amount INT);
INSERT INTO sales_long VALUES
('West','Q1',100),('West','Q2',150),('East','Q1',80),('East','Q2',90);

-- PIVOT via conditional aggregation — portable across every SQL engine
-- (some engines like SQL Server / Snowflake also offer a native PIVOT keyword,
--  but this CASE-based version works everywhere and shows the mechanics)
SELECT
    region,
    SUM(CASE WHEN quarter = 'Q1' THEN amount END) AS q1,   -- only counts Q1 rows, else NULL
    SUM(CASE WHEN quarter = 'Q2' THEN amount END) AS q2
FROM sales_long
GROUP BY region;

-- UNPIVOT back to long format from a wide table named sales_wide(region, q1, q2)
SELECT region, 'Q1' AS quarter, q1 AS amount FROM sales_wide
UNION ALL
SELECT region, 'Q2' AS quarter, q2 AS amount FROM sales_wide;
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("Pivot").getOrCreate()

data = [("West","Q1",100),("West","Q2",150),("East","Q1",80),("East","Q2",90)]
df = spark.createDataFrame(data, ["region","quarter","amount"])

# pivot is a native, built-in operation — no manual CASE statements needed
wide_df = df.groupBy("region").pivot("quarter").sum("amount")
wide_df.show()

# unpivot via stack(): turns N columns back into key/value row pairs
long_df = wide_df.selectExpr(
    "region",
    "stack(2, 'Q1', Q1, 'Q2', Q2) as (quarter, amount)"   # 2 = number of column pairs being unpivoted
)
long_df.show()
PYPython

data = {"region":["West","West","East","East"], "quarter":["Q1","Q2","Q1","Q2"], "amount":[100,150,80,90]}

String Manipulation & Regex

Clean up messy text fields and pull an email domain out of an address using a regular expression.

SQL
CREATE TABLE raw_contacts (name VARCHAR(50), email VARCHAR(50));
INSERT INTO raw_contacts VALUES ('  amy SMITH ', 'amy@workmail.com'), (' Ben jones', 'ben@home.org');

SELECT
    name,
    TRIM(name) AS name_trimmed,                          -- strip leading/trailing whitespace
    INITCAP(TRIM(name)) AS name_clean,                     -- "amy smith" -> "Amy Smith" (Postgres function)
    email,
    SUBSTRING(email FROM POSITION('@' IN email) + 1) AS domain,  -- everything after the @
    REGEXP_REPLACE(email, '@.*$', '') AS local_part        -- strip domain, keep the part before @
FROM raw_contacts;

Date & Time Operations

Extract parts of a date, compute the gap between two dates, and filter relative to a fixed reference point (kept fixed here so the examples are deterministic).

INSERT INTO orders VALUES
(1, '2024-03-04', '2024-03-09'),

    order_id,

Type Casting & Schema Enforcement

Raw string columns from a CSV need to become real numbers and dates — and a bad value shouldn't crash the whole load.

SQL
CREATE TABLE raw_import (id VARCHAR(10), price_str VARCHAR(20), date_str VARCHAR(20));
INSERT INTO raw_import VALUES ('1','19.99','2024-01-05'), ('2','not_a_price','2024-02-10');

-- Plain CAST throws an error the moment it hits 'not_a_price' — fine for
-- trusted data, dangerous for raw external input.
SELECT id, CAST(price_str AS DECIMAL(10,2)) AS price FROM raw_import;

-- TRY_CAST (SQL Server / Snowflake / BigQuery's SAFE_CAST) returns NULL on
-- failure instead of erroring out the whole query — the safer default
-- for ingesting untrusted source data.
SELECT
    id,
    TRY_CAST(price_str AS DECIMAL(10,2)) AS price,   -- NULL for the bad row, not an error
    TRY_CAST(date_str AS DATE) AS order_date
FROM raw_import;
PySpark
from pyspark.sql import SparkSession
from pyspark.sql.types import StructType, StructField, StringType, DecimalType, DateType
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("Casting").getOrCreate()

# Defining an explicit schema up front (rather than letting Spark infer one)
# is itself an interview-relevant practice — it's faster and avoids surprises.
schema = StructType([
    StructField("id", StringType(), True),
    StructField("price_str", StringType(), True),
    StructField("date_str", StringType(), True),
])
data = [("1","19.99","2024-01-05"), ("2","not_a_price","2024-02-10")]
df = spark.createDataFrame(data, schema)

# Spark's cast() never throws — an unconvertible value silently becomes null,
# which is the same safety behavior as SQL's TRY_CAST by default.
result = (
    df.withColumn("price", F.col("price_str").cast(DecimalType(10,2)))   # 'not_a_price' -> null
      .withColumn("order_date", F.to_date("date_str"))                     # invalid date -> null
)
result.show()
PYPython
import pandas as pd

data = {"id":["1","2"], "price_str":["19.99","not_a_price"], "date_str":["2024-01-05","2024-02-10"]}
df = pd.DataFrame(data)

# errors="coerce" is pandas' equivalent of TRY_CAST — unparseable values become NaN/NaT

Recursive CTEs & Hierarchy Traversal

Walk an org chart to find every employee reporting up to a given manager, at any depth — SQL has a native keyword for this; PySpark and pandas don't.

SQL
CREATE TABLE employees (emp_id INT, name VARCHAR(30), manager_id INT);
INSERT INTO employees VALUES
(1,'Alice', NULL),   -- CEO, no manager
(2,'Bob',   1),
(3,'Cleo',  1),
(4,'Drew',  2),
(5,'Evan',  4);

WITH RECURSIVE org_chart AS (
    -- Anchor: start from the manager we care about
    SELECT emp_id, name, manager_id, 1 AS depth
    FROM employees
    WHERE emp_id = 1

    UNION ALL

    -- Recursive step: find direct reports of everyone already in the
    -- result so far. Re-runs against its own growing output until a
    -- pass finds zero new rows, then stops automatically.
    SELECT e.emp_id, e.name, e.manager_id, oc.depth + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.emp_id
)
SELECT * FROM org_chart ORDER BY depth, emp_id;
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("Hierarchy").getOrCreate()

data = [(1,"Alice",None), (2,"Bob",1), (3,"Cleo",1), (4,"Drew",2), (5,"Evan",4)]
employees = spark.createDataFrame(data, ["emp_id","name","manager_id"])

# Spark SQL has no recursive CTE — the standard workaround is to loop,
# joining one level deeper each pass, until an iteration finds nothing new.
current_level = employees.filter(F.col("emp_id") == 1).withColumn("depth", F.lit(1))
result = current_level
depth = 1

while True:
    depth += 1
    next_level = (
        employees.join(current_level, employees.manager_id == current_level.emp_id)
                  .select(employees.emp_id, employees.name, employees.manager_id)
                  .withColumn("depth", F.lit(depth))
    )
    if next_level.count() == 0:          # no new direct reports found -> stop
        break
    result = result.unionByName(next_level)
    current_level = next_level

result.orderBy("depth", "emp_id").show()
PYPython
import pandas as pd

data = {"emp_id":[1,2,3,4,5], "name":["Alice","Bob","Cleo","Drew","Evan"], "manager_id":[None,1,1,2,4]}
df = pd.DataFrame(data)

# pandas has no recursive query either — walk the hierarchy level by level
# in plain Python, the same idea as the Spark loop above.
frontier = {1}                                              # start from manager_id 1's own row
all_rows = [df[df["emp_id"].isin(frontier)].assign(depth=1)]
depth = 1

while frontier:
    depth += 1
    next_rows = df[df["manager_id"].isin(frontier)]
    if next_rows.empty:
        break
    all_rows.append(next_rows.assign(depth=depth))
    frontier = set(next_rows["emp_id"])

result = pd.concat(all_rows).sort_values(["depth","emp_id"])
print(result)
Interview angle: if asked "how would you do this in Spark," the correct answer isn't "Spark doesn't support it" — it's the iterative join pattern shown here, plus a note that you'd add a cycle-detection guard (e.g. a max-iterations cap) in production, since a corrupted manager_id could otherwise loop forever.

SCD Type 2

A customer's address changes — expire the old "current" dimension row and insert a new one, preserving full history. The classic data-warehousing interview question.

SQL
CREATE TABLE dim_customer (
    customer_id INT,
    address     VARCHAR(50),
    start_date  DATE,
    end_date    DATE,        -- NULL means "this row is still active"
    is_current  BOOLEAN
);
INSERT INTO dim_customer VALUES (1, '12 Oak St', '2023-01-01', NULL, TRUE);

-- staging_customer(customer_id, new_address, change_date) holds today's incoming change

-- Step 1: expire the old current row, but ONLY if the address actually changed
UPDATE dim_customer d
SET end_date = s.change_date, is_current = FALSE
FROM staging_customer s
WHERE d.customer_id = s.customer_id
  AND d.is_current = TRUE
  AND d.address <> s.new_address;

-- Step 2: insert the new current row
INSERT INTO dim_customer (customer_id, address, start_date, end_date, is_current)
SELECT s.customer_id, s.new_address, s.change_date, NULL, TRUE
FROM staging_customer s
JOIN dim_customer d ON d.customer_id = s.customer_id
WHERE d.end_date = s.change_date;     -- the row we just expired in step 1
-- (Some engines support a single MERGE statement instead of these two steps —
--  same idea, fewer round trips.)
PySpark
# Plain Spark DataFrames can't update rows in place, so real SCD2 pipelines
# almost always sit on top of Delta Lake (the delta-spark package), which
# adds row-level UPDATE/MERGE on top of Spark.
from delta.tables import DeltaTable
from pyspark.sql import functions as F

dim_customer = DeltaTable.forPath(spark, "/path/to/dim_customer")   # existing Delta table
staging = spark.createDataFrame(
    [(1, "45 Maple Ave", "2024-06-01")],
    ["customer_id", "new_address", "change_date"]
)

# Step 1: expire current rows whose address changed
(dim_customer.alias("d")
    .merge(staging.alias("s"), "d.customer_id = s.customer_id AND d.is_current = true")
    .whenMatchedUpdate(
        condition="d.address <> s.new_address",
        set={"end_date": "s.change_date", "is_current": "false"}
    )
    .execute()
)

# Step 2: append a fresh "current" row for every customer that changed
new_rows = staging.select(
    F.col("customer_id"),
    F.col("new_address").alias("address"),
    F.col("change_date").alias("start_date"),
    F.lit(None).alias("end_date"),
    F.lit(True).alias("is_current"),
)
new_rows.write.format("delta").mode("append").save("/path/to/dim_customer")
PYPython
import pandas as pd

dim_customer = pd.DataFrame({
    "customer_id": [1], "address": ["12 Oak St"],
    "start_date": ["2023-01-01"], "end_date": [None], "is_current": [True],
})
staging = pd.DataFrame({"customer_id": [1], "new_address": ["45 Maple Ave"], "change_date": ["2024-06-01"]})

# pandas has no MERGE statement — SCD2 has to be written as explicit steps,
# which doubles as a clear explanation of what MERGE does under the hood.
merged = dim_customer.merge(staging, on="customer_id", how="left")
changed = merged["is_current"] & (merged["address"] != merged["new_address"])

# Step 1: expire the changed rows
dim_customer.loc[changed, "end_date"] = merged.loc[changed, "change_date"]
dim_customer.loc[changed, "is_current"] = False

# Step 2: append new current rows for whatever changed
new_rows = merged.loc[changed, ["customer_id", "new_address", "change_date"]].rename(
    columns={"new_address": "address", "change_date": "start_date"}
)
new_rows["end_date"] = None
new_rows["is_current"] = True

dim_customer = pd.concat([dim_customer, new_rows], ignore_index=True)
print(dim_customer)
Interview angle: SCD2 keeps full history (multiple rows per entity, an is_current flag), while SCD1 just overwrites in place and loses history — naming that distinction unprompted is usually worth more than the code itself. Also worth mentioning: this is precisely the gap that made Delta Lake / Iceberg / Hudi necessary on top of plain Spark.

Upsert / Merge (Incremental Load)

A nightly batch brings updates to existing orders and a few brand-new ones — update what exists, insert what doesn't, in one pass.

SQL
CREATE TABLE orders (order_id INT PRIMARY KEY, status VARCHAR(20), amount INT);
INSERT INTO orders VALUES (1,'pending',100),(2,'shipped',250);

-- staging_orders(order_id, status, amount) holds today's incremental batch

MERGE INTO orders AS target
USING staging_orders AS source
ON target.order_id = source.order_id
WHEN MATCHED THEN
    UPDATE SET status = source.status, amount = source.amount   -- existing order changed
WHEN NOT MATCHED THEN
    INSERT (order_id, status, amount)
    VALUES (source.order_id, source.status, source.amount);     -- brand-new order
PySpark
# With Delta Lake, this mirrors SQL's MERGE almost exactly:
from delta.tables import DeltaTable

target = DeltaTable.forPath(spark, "/path/to/orders")
staging = spark.createDataFrame([(2,"delivered",250),(3,"pending",75)], ["order_id","status","amount"])

(target.alias("t")
    .merge(staging.alias("s"), "t.order_id = s.order_id")
    .whenMatchedUpdate(set={"status": "s.status", "amount": "s.amount"})
    .whenNotMatchedInsert(values={
        "order_id": "s.order_id", "status": "s.status", "amount": "s.amount"
    })
    .execute()
)

# Without Delta (plain Spark has no row-level update), the common workaround:
# stack both sources, tag staging rows as higher priority, then keep one row
# per order_id by ranking on that priority.
from pyspark.sql import functions as F
from pyspark.sql.window import Window

target_df = spark.createDataFrame([(1,"pending",100),(2,"shipped",250)], ["order_id","status","amount"])
combined = (
    target_df.withColumn("priority", F.lit(0))                      # 0 = old data
              .unionByName(staging.withColumn("priority", F.lit(1)))   # 1 = new data, wins ties
)
w = Window.partitionBy("order_id").orderBy(F.col("priority").desc())
result = (
    combined.withColumn("rn", F.row_number().over(w))
            .filter(F.col("rn") == 1)
            .drop("priority", "rn")
)
result.show()
PYPython
import pandas as pd

orders  = pd.DataFrame({"order_id":[1,2], "status":["pending","shipped"], "amount":[100,250]}).set_index("order_id")
staging = pd.DataFrame({"order_id":[2,3], "status":["delivered","pending"], "amount":[250,75]}).set_index("order_id")

# update() overwrites matching index rows in place — the WHEN MATCHED half of MERGE
orders.update(staging)

# concat the rows whose order_id wasn't already present — the WHEN NOT MATCHED half
new_orders = staging[~staging.index.isin(orders.index)]
orders = pd.concat([orders, new_orders])

print(orders.reset_index())
Interview angle: this is the same shape as SCD2 (C.2) but without preserving history — make sure to state out loud which one the interviewer actually wants, since "upsert" and "SCD2" get used interchangeably in casual conversation but produce very different table designs.

Gaps & Islands (Sessionization)

Group a user's login events into sessions, starting a new session whenever the gap since the last login exceeds 30 minutes.

SQL
CREATE TABLE logins (user_id INT, login_time TIMESTAMP);
INSERT INTO logins VALUES
(1,'2024-01-01 09:00'),(1,'2024-01-01 09:10'),(1,'2024-01-01 09:50'),
(1,'2024-01-01 11:00'),(1,'2024-01-01 11:05');

WITH gaps AS (
    SELECT
        user_id, login_time,
        LAG(login_time) OVER (PARTITION BY user_id ORDER BY login_time) AS prev_login
    FROM logins
),
flagged AS (
    SELECT
        user_id, login_time,
        CASE
            WHEN prev_login IS NULL THEN 1                                  -- first event ever: new session
            WHEN login_time - prev_login > INTERVAL '30 minutes' THEN 1       -- gap too big: new session
            ELSE 0
        END AS is_new_session
    FROM gaps
)
SELECT
    user_id, login_time,
    SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY login_time) AS session_id  -- running count of flags
FROM flagged;
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder.appName("Sessionize").getOrCreate()

data = [(1,"2024-01-01 09:00"),(1,"2024-01-01 09:10"),(1,"2024-01-01 09:50"),
        (1,"2024-01-01 11:00"),(1,"2024-01-01 11:05")]
df = spark.createDataFrame(data, ["user_id","login_time"])
df = df.withColumn("login_time", F.to_timestamp("login_time"))

w = Window.partitionBy("user_id").orderBy("login_time")

flagged = (
    df.withColumn("prev_login", F.lag("login_time").over(w))                                     # previous row's time
      .withColumn(
          "is_new_session",
          F.when(F.col("prev_login").isNull(), 1)                                                  # first event
           .when(F.col("login_time").cast("long") - F.col("prev_login").cast("long") > 1800, 1)      # gap > 1800s (30 min)
           .otherwise(0)
      )
)

result = flagged.withColumn(
    "session_id",

SQL

-- of a data lake (Hive, Athena, Spark SQL, Trino) use this exact pattern to

CREATE EXTERNAL TABLE orders (
    order_id    INT,

D.2

UDFs vs Built-ins (Performance)

Tier customers by price using a row-by-row Python function versus a native built-in — the performance gap behind this is one of the most common Spark and pandas follow-up questions.

SQL
CREATE TABLE products (product_id INT, price DECIMAL(10,2));
INSERT INTO products VALUES (1,45.00),(2,210.00),(3,899.00);

-- A scalar user-defined function (Postgres syntax) runs once per row, outside
-- the query planner's view — the optimizer can't see inside it or rewrite around it.
CREATE FUNCTION price_tier(p DECIMAL) RETURNS VARCHAR AS $$
BEGIN
    IF p >= 500 THEN RETURN 'High';
    ELSIF p >= 100 THEN RETURN 'Mid';
    ELSE RETURN 'Low';
    END IF;
END;
$$ LANGUAGE plpgsql;

SELECT product_id, price, price_tier(price) AS tier FROM products;   -- UDF call

-- The built-in equivalent: the optimizer fully understands CASE and can
-- often push it down, vectorize it, or fold it into other operations.
SELECT
    product_id, price,
    CASE WHEN price >= 500 THEN 'High'
         WHEN price >= 100 THEN 'Mid'
         ELSE 'Low' END AS tier
FROM products;
PySpark
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.types import StringType

spark = SparkSession.builder.appName("UDFvsBuiltin").getOrCreate()

data = [(1, 45.00), (2, 210.00), (3, 899.00)]
df = spark.createDataFrame(data, ["product_id", "price"])

# A Python UDF: every row gets serialized out of the JVM into a Python
# process, processed one at a time, then serialized back. This bypasses
# Catalyst (Spark's query optimizer) entirely — it's a black box to Spark.
def price_tier_udf(price):
    if price >= 500: return "High"
    elif price >= 100: return "Mid"
    else: return "Low"

price_tier = F.udf(price_tier_udf, StringType())
df.withColumn("tier", price_tier(F.col("price"))).show()

# The built-in equivalent: stays inside the JVM, Catalyst can optimize it,
# and on most workloads it's measurably faster at scale.
df.withColumn(
    "tier",
    F.when(F.col("price") >= 500, "High")
     .when(F.col("price") >= 100, "Mid")
     .otherwise("Low")
).show()
PYPython

import numpy as np

"Prefer built-ins over UDFs when one exists" is a one-line answer that signals real engine knowledge.

Partitioning & Broadcast Joins

Joining a huge fact table against a small dimension table — broadcasting the small side avoids an expensive shuffle of the large one. A pure distributed-engine concept.

SQL
-- Spark SQL's broadcast hint — the SQL-side way to ask the engine to ship
-- the small table to every executor instead of shuffling the large one.
SELECT /*+ BROADCAST(dim_region) */
    f.order_id, f.amount, dim_region.region_name
FROM fact_orders f
JOIN dim_region ON f.region_id = dim_region.region_id;

-- On a traditional single-node engine like Postgres there's no "broadcast"
-- concept to hint at — the query optimizer already picks a join strategy
-- (hash join, nested loop, merge join) based on table statistics automatically.
-- EXPLAIN shows you what it chose:
EXPLAIN SELECT f.order_id, f.amount, d.region_name
FROM fact_orders f JOIN dim_region d ON f.region_id = d.region_id;
PySpark
from pyspark.sql import SparkSession

# broadcast() tells Spark to instead copy the small table to every executor,

Handling Skewed Data (Salting)

One join key has wildly more rows than the rest, so a single task does almost all the work while every other task sits idle — salting spreads that key artificially across more partitions.

SQL
-- Salting in Spark SQL: append a small random integer to the skewed key on
-- both sides of the join so rows that used to land on one partition spread
-- across several, then strip the salt back off after joining.
SELECT
    f.order_id, f.customer_id, d.customer_name
FROM (
    SELECT *, CONCAT(customer_id, '_', CAST(FLOOR(RAND() * 10) AS INT)) AS salted_key
    FROM fact_orders f
) f
JOIN (
    SELECT *, CONCAT(customer_id, '_', salt) AS salted_key
    FROM dim_customer
    CROSS JOIN (SELECT EXPLODE(SEQUENCE(0, 9)) AS salt)   -- replicate each dim row 10x, once per salt value
) d
ON f.salted_key = d.salted_key;
-- A single-node engine like Postgres has no concept of skewed task
-- distribution at all — there's only one process, so there's nothing to
-- rebalance across. Salting is specifically a distributed-shuffle fix.
PySpark
from pyspark.sql import functions as F

# Say customer_id 42 alone accounts for 40% of all rows in fact_orders —
# every task handling that key becomes a bottleneck. Salting fans it out.
SALT_RANGE = 10

fact_salted = fact_orders.withColumn(
    "salted_key",
    F.concat(F.col("customer_id"), F.lit("_"), (F.rand() * SALT_RANGE).cast("int"))
)

# Replicate each dimension row once per possible salt value, so every
# salted fact row still has a matching salted dimension row to join against.
salts = spark.range(SALT_RANGE).withColumnRenamed("id", "salt")
dim_salted = (
    dim_customer.crossJoin(salts)
                .withColumn("salted_key", F.concat(F.col("customer_id"), F.lit("_"), F.col("salt")))
)

result = (
    fact_salted.join(dim_salted, on="salted_key")
               .drop("salted_key", "salt")     # strip the salt back off, it was only a join helper
)
result.show()
PYPython
No code — see note
Skew is a distributed compute problem — it happens when one partition gets far more rows than the cluster's other workers and becomes a bottleneck. pandas has no partitions or workers; a join just runs as one in-memory hash join on a single core. The closest single-machine analogue is running out of RAM on a huge join, which you'd solve by chunking the data (pd.read_csv(chunksize=...)) rather than by salting a key — a different problem with a different fix.
Interview angle: describe the symptom before the fix — one or two tasks in the Spark UI taking far longer than the rest while everything else finishes quickly is the tell-tale sign of skew. Salting fixes the symmetry of the join; it doesn't reduce total work, it redistributes it more evenly.

Caching & Explain Plans

Reuse an expensive intermediate result instead of recomputing it, and read a query's execution plan to understand what the engine is actually doing.

SQL
-- EXPLAIN (ANALYZE) shows the real execution plan: which join algorithm
-- was chosen, whether an index was used, and where time was actually spent.
EXPLAIN ANALYZE
SELECT customer_id, SUM(amount)
FROM orders
GROUP BY customer_id;

-- SQL engines don't have an in-session ".cache()" call; the equivalent of
-- "materialize this once, reuse it many times" is a materialized view or
-- a temp table that's computed once and queried repeatedly afterward.
CREATE MATERIALIZED VIEW customer_totals AS
SELECT customer_id, SUM(amount) AS total_spend
FROM orders
GROUP BY customer_id;

REFRESH MATERIALIZED VIEW customer_totals;   -- recompute it when the underlying data changes
PySpark
from pyspark.sql import functions as F

orders = spark.read.parquet("/path/to/orders")

expensive_df = (
    orders.groupBy("customer_id")
          .agg(F.sum("amount").alias("total_spend"))
)

# Without caching, every action below (.count(), .show(), the join) would
# re-run the ENTIRE groupBy/agg from the original Parquet files, every time —
# Spark is lazy and doesn't remember results unless told to.
expensive_df.cache()       # materialize it in memory after the first action triggers it
expensive_df.count()       # this first action actually does the work and populates the cache
expensive_df.show()        # this reuses the cached result instead of recomputing

expensive_df.explain()     # physical plan — look for "InMemoryTableScan" confirming the cache is used

expensive_df.unpersist()   # free the cached memory once you're done with it
PYPython
No code — see note

There's nothing to call .explain() on, because there's no plan; what you wrote is exactly what ran. The only "caching" available is the ordinary one: store the result of an expensive computation in a variable once, and reuse that variable instead of recomputing.

# reuse expensive_df as many times as needed — it's just sitting in memory already

Comprehensions & Generators

List comprehensions for quick in-memory transforms, and generators for streaming a file too large to fit in memory all at once.

]

# a for-loop that appends to a list, just the more idiomatic Python form.

def read_large_file(path):
    """A generator yields one line at a time instead of loading the whole
    file into memory — essential once a source file is bigger than RAM."""
    with open(path, "r") as f:
        for line in f:
            yield line.strip()

# Nothing inside read_large_file() actually runs until you iterate over it —
# that's the "lazy" part of a generator.
for line in read_large_file("huge_input.csv"):
    if line.startswith("ERROR"):
        print(line)
        break   # we can stop early without ever reading the rest of the file into memory

Working with APIs & JSON Parsing

import requests

def fetch_all_pages(base_url, page_size=100):
    """Many APIs paginate results — keep requesting the next page until the
    API signals there isn't one, instead of assuming everything fits in a single call."""
    all_records = []
    page = 1
    while True:
        try:
            response = requests.get(base_url, params={"page": page, "page_size": page_size}, timeout=10)
            response.raise_for_status()        # raises an exception for any 4xx/5xx status code
        except requests.exceptions.RequestException as e:
            print(f"Request failed on page {page}: {e}")
            break

        payload = response.json()
        records = payload.get("results", [])
        if not records:
            break                                # empty page = no more data, stop here

        all_records.extend(records)
        page += 1

    return all_records

data = fetch_all_pages("https://api.example.com/orders")
order_ids = [record["id"] for record in data if "id" in record]    # nested-field extraction with a safety guard
Interview angle: raise_for_status() plus a specific except on requests.exceptions.RequestException is the detail that separates "knows requests exists" from "has actually built something that talks to a flaky third-party API in production" — a network call that silently returns bad data is worse than one that fails loudly.

Simple Pipeline Class (OOP)

Structure an extract-transform-load script as a class with chainable methods, so each stage is independently testable and the run order is explicit.

PYPython
class ETLPipeline:
    """A minimal extract-transform-load pipeline structured as a class so
    each stage is independently testable and the run order is explicit."""

    def __init__(self, source_path, destination_path):
        self.source_path = source_path
        self.destination_path = destination_path
        self.data = None

    def extract(self):
        with open(self.source_path, "r") as f:
            self.data = [line.strip().split(",") for line in f]
        return self                              # returning self enables method chaining below

    def transform(self):
        rows = self.data[1:]                      # drop the header row
        # keep only rows where the amount column (index 2) parses as a number
        self.data = [r for r in rows if r[2].replace(".", "", 1).isdigit()]
        return self

    def load(self):
        with open(self.destination_path, "w") as f:
            for row in self.data:
                f.write(",".join(row) + "\n")
        return self

    def run(self):
        return self.extract().transform().load()    # each step returns self, so calls chain naturally

pipeline = ETLPipeline("raw_orders.csv", "clean_orders.csv")
pipeline.run()
Interview angle: having each stage return self is what enables the chained .extract().transform().load() call in run() — it's a small pattern, but mentioning it by name (method chaining / fluent interface) signals you've structured pipelines this way before, not just written one long script top to bottom.

Find Duplicates in a List

A classic technical-screen warmup, usually the first question before the conversation moves into SQL or Spark territory.

PYPython
nums = [4, 5, 5, 7, 8, 8, 8, 9]

# A set tracks values already seen; the first time a number repeats, it
# goes into the duplicates set. This is O(n) instead of the O(n^2) you'd
# get from comparing every pair of elements against each other.
seen = set()
duplicates = set()
for n in nums:
    if n in seen:
        duplicates.add(n)
    seen.add(n)

print(duplicates)   # {5, 8}

# A shorter version using collections.Counter — useful when you also want
# to know HOW MANY times each value repeated, not just whether it did.
from collections import Counter
counts = Counter(nums)
duplicates_v2 = {value for value, count in counts.items() if count > 1}
print(duplicates_v2)   # {5, 8}
Interview angle: the naive answer compares every pair of elements (O(n²)) — the moment you mention tracking "seen so far" in a set, you've signaled an O(n) solution, which is usually exactly what the interviewer is listening for regardless of how simple the question sounds.

Count Frequency of Elements

Build a frequency table by hand, then with the standard library helper built exactly for this — knowing both shows you understand the underlying pattern, not just the shortcut.

PYPython
from collections import Counter

words = ["error", "warn", "error", "info", "error", "warn"]

# Manual approach: dict.get(key, default) avoids a KeyError on the first
# time a key is seen, which a plain freq[w] += 1 would raise immediately.
freq = {}
for w in words:
    freq[w] = freq.get(w, 0) + 1
print(freq)   # {'error': 3, 'warn': 2, 'info': 1}

# Idiomatic approach: Counter builds the same frequency mapping in one call,
# and .most_common(n) returns the top n entries sorted by count, descending.
freq_counter = Counter(words)
print(freq_counter)                 # Counter({'error': 3, 'warn': 2, 'info': 1})
print(freq_counter.most_common(2))  # [('error', 3), ('warn', 2)]
Interview angle: writing the manual version first shows you understand why dict.get(key, 0) is needed at all; reaching for Counter afterward shows you also know when to stop reinventing the standard library. Both halves of that answer matter.

# set(records) removes duplicates but does NOT preserve the original order.
# dict.fromkeys() does, because dict keys have kept insertion order since
# Python 3.7, and a duplicate key just overwrites in place rather than
# moving — so the first occurrence's position is what's kept.
unique_ordered = list(dict.fromkeys(records))
print(unique_ordered)   # [3, 1, 2, 4]

# The manual equivalent — worth knowing if asked "how does that trick work?"
seen = set()
unique_manual = []
for r in records:
    if r not in seen:
        unique_manual.append(r)
        seen.add(r)
print(unique_manual)   # [3, 1, 2, 4]
Interview angle: if you reach for list(set(records)) as the answer, say out loud that it doesn't preserve order — that single caveat is often the entire point of the question, especially when the data being deduped is something like a sequence of events or log lines where order is meaningful.

Group Items by a Key

The plain-Python ancestor of every GROUP BY / groupby() question elsewhere in this reference — worth being fluent in before reaching for a DataFrame.

PYPython
from collections import defaultdict

orders = [
    {"region": "West", "amount": 10},
    {"region": "East", "amount": 20},
    {"region": "West", "amount": 5},
]

# defaultdict(list) supplies an empty list automatically the first time a
# new key is touched, avoiding a manual "if key not in dict: dict[key] = []"
# check before every single append.
grouped = defaultdict(list)
for order in orders:
    grouped[order["region"]].append(order["amount"])

print(dict(grouped))   # {'West': [10, 5], 'East': [20]}

# Once grouped, it's common to reduce each group down to one summary value —
# the plain-Python equivalent of a GROUP BY + SUM.
totals = {region: sum(amounts) for region, amounts in grouped.items()}
print(totals)   # {'West': 15, 'East': 20}
Interview angle: this is the exact mental model behind every GROUP BY / groupBy() / .groupby() question elsewhere in this guide, minus the engine doing the bucketing for you — being able to write it by hand with a plain dict is what proves you understand grouping, not just the syntax for invoking it.
F.5

Two Sum

Probably the single most-asked array question across every kind of technical interview, data engineering included — the hashmap trick is the entire point.

PYPython
def two_sum(nums, target):
    """Return the indices of the two numbers that add up to target, or
    None if no such pair exists. Runs in O(n) by remembering every value
    seen so far, instead of comparing every pair (which would be O(n^2))."""
    seen = {}                        # maps a number -> the index where it was seen
    for i, n in enumerate(nums):
        complement = target - n
        if complement in seen:
            return [seen[complement], i]
        seen[n] = i                  # remember this number for later pairs to check against
    return None

print(two_sum([2, 7, 11, 15], 9))   # [0, 1]  -> nums[0] + nums[1] == 9
print(two_sum([3, 2, 4], 6))         # [1, 2]  -> nums[1] + nums[2] == 6
print(two_sum([1, 2, 3], 100))       # None    -> no pair sums to 100
Interview angle: the naive double-loop solution is O(n²) and will get you partial credit at best — the hashmap version trades a bit of extra memory (the seen dict) for a single O(n) pass, and explaining that trade-off out loud is worth as much as writing the code itself.

Merge Two Dictionaries

Combining config dicts, default values with overrides, or partial records — and handling what happens when both sides define the same key.

PYPython
defaults = {"timeout": 30, "retries": 3, "region": "us-east-1"}
overrides = {"retries": 5, "region": "eu-west-1"}

# The | operator (Python 3.9+) merges two dicts; on a key collision, the
# RIGHT-hand dict wins — here, overrides' values replace defaults'.
merged = defaults | overrides
print(merged)   # {'timeout': 30, 'retries': 5, 'region': 'eu-west-1'}

# Pre-3.9 equivalent — also useful once the merge logic needs to be more
# than "right side wins":
merged_manual = dict(defaults)        # copy first, so the original isn't mutated
for key, value in overrides.items():
    merged_manual[key] = value
print(merged_manual)   # same result as above

# Summing values on conflict instead of overwriting them:
counts_a = {"x": 1, "y": 2}
counts_b = {"y": 3, "z": 4}
summed = {k: counts_a.get(k, 0) + counts_b.get(k, 0) for k in counts_a.keys() | counts_b.keys()}
print(summed)   # {'x': 1, 'y': 5, 'z': 4}
Interview angle: "merge two dicts" sounds trivial until the interviewer asks what should happen on a key collision — "the right side just overwrites" is one valid answer, but showing you can also sum, append, or otherwise combine colliding values (as in the last example) demonstrates you're thinking about the actual data, not just memorizing the | operator.
F.7

Flatten a Nested List

Collapse arbitrarily nested lists into one flat list — common when normalizing inconsistent or hierarchical source data before loading it anywhere.

PYPython
nested = [[1, 2, [3, 4]], [5], [6, [7, [8, 9]]]]

# A recursive function handles arbitrary nesting depth — a fixed number of
# loops would only ever handle a fixed number of levels correctly.
def flatten(items):
    result = []
    for item in items:
        if isinstance(item, list):
            result.extend(flatten(item))    # recurse into the nested list
        else:
            result.append(item)
    return result

print(flatten(nested))   # [1, 2, 3, 4, 5, 6, 7, 8, 9]

# A one-level-only flatten (when the nesting is known to be exactly 2 levels
# deep, e.g. a list of rows) is simpler and doesn't need recursion at all:
rows = [[1, 2], [3, 4], [5, 6]]
flat_one_level = [value for row in rows for value in row]   # nested comprehension
print(flat_one_level)   # [1, 2, 3, 4, 5, 6]
Interview angle: ask (or state out loud) whether the nesting depth is fixed or arbitrary before picking an approach — a nested comprehension is the cleaner answer for a fixed, known depth, but it silently produces wrong results on deeper or irregular nesting, which is exactly when recursion becomes necessary.

Sort a List of Dicts or Tuples by a Key

Sorting structured records by a field other than their natural order — and the difference between a function that mutates and one that doesn't.

PYPython
employees = [
    {"name": "Alice", "salary": 9000},
    {"name": "Bob", "salary": 8500},
    {"name": "Charlie", "salary": 11000},
]

# key= takes a function that extracts the value to sort by from each item.
# sorted() always returns a NEW list and never mutates the original,
# unlike list.sort() which sorts in place and returns None.
by_salary_desc = sorted(employees, key=lambda e: e["salary"], reverse=True)
print([e["name"] for e in by_salary_desc])   # ['Charlie', 'Alice', 'Bob']

Set Operations in Plain Python

Union, intersection, difference, and symmetric difference using Python's built-in set type — and why sets make membership checks fast.

PYPython
team_a = {"amy", "ben", "cleo"}
team_b = {"ben", "cleo", "drew"}

print(team_a | team_b)   # union: everyone in either team        -> {'amy','ben','cleo','drew'}
print(team_a & team_b)   # intersection: in both teams           -> {'ben', 'cleo'}
print(team_a - team_b)   # difference: in A but not B            -> {'amy'}
print(team_a ^ team_b)   # symmetric difference: in exactly one  -> {'amy', 'drew'}

# Membership testing on a set is O(1) average case, versus O(n) for a list
# scan — this is exactly why "convert to a set first" is a common
# optimization when checking many values for membership repeatedly.
big_list = list(range(1_000_000))
big_set = set(big_list)
print(999_999 in big_set)   # fast: O(1) average-case lookup, not a linear scan
Interview angle: the operators (| & - ^) are exactly the same set algebra used in the SQL/PySpark/pandas set-operations topic earlier in this reference (UNION, INTERSECT, EXCEPT) — pointing that connection out explicitly shows you see the same concept underneath three different syntaxes, which is a more impressive answer than any one of the syntaxes alone.

Anagram / Character Frequency Check

Two equally valid one-line approaches to checking whether two strings are anagrams of each other.

PYPython
from collections import Counter

def is_anagram(word1, word2):
    """Two words are anagrams if they contain exactly the same letters with
    exactly the same counts, just rearranged — so comparing character
    frequencies (via Counter) settles the question in a single line."""
    return Counter(word1.lower()) == Counter(word2.lower())

print(is_anagram("listen", "silent"))   # True
print(is_anagram("hello", "world"))      # False

# Sorting each string's characters is an equally common one-line alternative —
# two strings are anagrams exactly when their sorted character lists match.
def is_anagram_sorted(word1, word2):
    return sorted(word1.lower()) == sorted(word2.lower())

print(is_anagram_sorted("listen", "silent"))   # True
Interview angle: the Counter version is O(n) while the sorted-characters version is O(n log n) because of the sort — mentioning that difference unprompted is a small detail that signals you think about complexity by default, not just when explicitly asked to.

Extract from a REST API (Incremental, Watermark-Based)

Pulling the entire dataset from an API on every run doesn't scale — a watermark lets each run fetch only what changed since the last successful pull.

PySpark
import requests
from pyspark.sql import functions as F

spark = SparkSession.builder.appName("ExtractOrdersAPI").getOrCreate()

# Spark has no built-in HTTP client — calling a REST API is still plain
# Python running on the driver, exactly like the non-Spark version. What
# changes is where the watermark lives and what happens to the result
# once it's fetched.
def get_watermark(path):
    try:
        row = spark.read.json(path).collect()[0]
        return row["last_extracted_at"]
    except Exception:
        return "1970-01-01T00:00:00Z"    # no prior watermark file -> pull everything

def save_watermark(path, timestamp):
    spark.createDataFrame([(timestamp,)], ["last_extracted_at"]).write.mode("overwrite").json(path)

since = get_watermark(watermark_path)

response = requests.get("https://api.example.com/orders", params={"updated_since": since}, timeout=10)
response.raise_for_status()
records = response.json()["results"]

# Convert the fetched JSON straight into a Spark DataFrame so every stage
# after this point runs distributed, not just the HTTP call itself.
df = spark.createDataFrame(records)

if records:
    newest_timestamp = df.agg(F.max("updated_at")).collect()[0][0]
    save_watermark(watermark_path, newest_timestamp)

print(f"Extracted {df.count()} new/updated records since {since}")

    re-fetching the entire dataset from the beginning every time."""

        return json.loads(WATERMARK_FILE.read_text())["last_extracted_at"]

# onto one shared schema BEFORE combining. Without this, unionByName either
# raises on a column it doesn't recognize, or silently fills mismatches
# with null if allowMissingColumns is set.
COLUMN_MAP = {"OrderID": "order_id", "id": "order_id", "Total": "amount", "order_total": "amount"}

]

Transform — Clean, Standardize, Validate

One function that runs every cleaning rule in a fixed, documented order on the combined raw data — deduplication, safe casting, required-field checks, and category normalization all in one place.

PySpark
from pyspark.sql import functions as F
from pyspark.sql.window import Window

def transform_orders(raw_df):
    """Runs the same fixed sequence of cleaning steps as the pandas version
    — deduplication, safe casting, required-field checks, and category
    normalization — expressed as DataFrame transformations instead."""
    df = raw_df

    # 1. Deduplicate: keep the most recently dated record per order_id.
    # Spark has no drop_duplicates(keep="last"); rank within a window instead.
    w = Window.partitionBy("order_id").orderBy(F.col("order_date").desc())
    df = (df.withColumn("rn", F.row_number().over(w))
            .filter(F.col("rn") == 1)
            .drop("rn"))

    # 2. Safe type casting: an invalid value becomes null instead of
    # raising and crashing the whole job
    df = (df.withColumn("amount", F.col("amount").cast("double"))
            .withColumn("order_date", F.to_date("order_date")))

    # 3. Drop rows missing a value that's genuinely required downstream
    before = df.count()
    df = df.dropna(subset=["order_id", "amount", "order_date"])
    print(f"Dropped {before - df.count()} rows with missing required fields")

    # 4. Business rule: negative amounts are a known upstream bug — clip
    # rather than drop, since the rest of the row is still valid
    df = df.withColumn("amount", F.when(F.col("amount") < 0, 0).otherwise(F.col("amount")))

    # 5. Standardize a free-text field into a fixed set of categories
    df = df.withColumn("status", F.lower(F.trim(F.col("status"))))
    df = df.replace({"complete": "completed", "cancelled": "canceled"}, subset=["status"])

    return df

clean_df = transform_orders(combined)
print(f"Transformed to {clean_df.count()} clean rows")

import pandas as pd

def transform_orders(raw_df):
    """Runs the full set of cleaning steps in a fixed order. Keeping every
    rule in one function makes the transform logic independently testable,
    separate from however the data was extracted or however it gets loaded."""
    df = raw_df.copy()

    # 1. Deduplicate: keep the most recently dated record per order_id
    df = df.sort_values("order_date").drop_duplicates(subset="order_id", keep="last")

    # 2. Safe type casting: bad values become null instead of crashing the pipeline
    df["amount"] = pd.to_numeric(df["amount"], errors="coerce")
    df["order_date"] = pd.to_datetime(df["order_date"], errors="coerce")

    # 3. Drop rows missing a value that's genuinely required downstream
    before = len(df)
    df = df.dropna(subset=["order_id", "amount", "order_date"])
    print(f"Dropped {before - len(df)} rows with missing required fields")

    # 4. Business rule: negative amounts are a known upstream bug — clip
    # rather than drop, since the rest of the row (customer, date) is still valid
    df["amount"] = df["amount"].clip(lower=0)

    # 5. Standardize a free-text field into a fixed set of categories
    df["status"] = df["status"].str.strip().str.lower()
    df["status"] = df["status"].replace({"complete": "completed", "cancelled": "canceled"})

Load — Idempotent Upsert into a Database

Write the transformed data into the target table so that re-running the same batch twice never creates duplicates or corrupts existing rows.

PySpark
# Spark's JDBC writer can append or overwrite a whole table, but it has
# no built-in upsert. The standard pattern: stage the batch in a temp
# table, then let the database's own MERGE/ON CONFLICT do the rest.
clean_df.write.jdbc(
    url=jdbc_url,
    table="orders_staging",
    mode="overwrite",        # the staging table is fully replaced on every run
    properties=connection_props,
)

# The actual upsert runs as one SQL statement against the database itself,
# executed over a plain JDBC/psycopg2 connection from the driver — Spark's
# job was only to get the batch staged there.
import psycopg2

conn = psycopg2.connect(host="db.internal", dbname="sales", user="etl_user", password="secret")
with conn, conn.cursor() as cur:
    cur.execute("""
        INSERT INTO orders (order_id, customer_id, amount, order_date)
        SELECT order_id, customer_id, amount, order_date FROM orders_staging
        ON CONFLICT (order_id) DO UPDATE
        SET amount = EXCLUDED.amount, order_date = EXCLUDED.order_date
    """)
conn.close()

print(f"Staged and merged {clean_df.count()} rows")
PYPython
import sqlalchemy as sa
from sqlalchemy.dialects.postgresql import insert as pg_insert

engine = sa.create_engine("postgresql+psycopg2://etl_user:secret@db.internal:5432/sales")
metadata = sa.MetaData()
orders_table = sa.Table("orders", metadata, autoload_with=engine)   # reflects the existing table's columns

def load_orders(df, engine, table):
    records = df.to_dict(orient="records")
    if not records:
        return

    stmt = pg_insert(table).values(records)
    # ON CONFLICT DO UPDATE: if order_id already exists, overwrite it with the
    # new values instead of erroring — this is what makes reruns idempotent.
    update_cols = {c.name: c for c in stmt.excluded if c.name != "order_id"}
    stmt = stmt.on_conflict_do_update(index_elements=["order_id"], set_=update_cols)

    with engine.begin() as conn:    # a transaction: every row commits together, or none do
        conn.execute(stmt)

load_orders(clean_df, engine, orders_table)
print(f"Loaded {len(clean_df)} rows (inserted new, updated existing)")
Interview angle: "Idempotent" is the word to use here: a load step is idempotent if running it twice with the same input produces the same end state as running it once. ON CONFLICT DO UPDATE is Postgres-specific syntax — MySQL's analogue is ON DUPLICATE KEY UPDATE, and SQL Server/Snowflake would use a MERGE statement, the same one covered in C.3. Spark/JDBC writes have no native upsert either — the fix is the same idea as the plain-Python version, just split across two systems: Spark stages the batch, and the database's own ON CONFLICT does the actual conflict resolution.

from pyspark.sql import functions as F
from datetime import datetime, timezone
import json

def load_to_data_lake(df, base_path, partition_col="order_date"):
    df = df.withColumn("load_partition", F.date_format(F.col(partition_col), "yyyy-MM-dd"))

    (df.write
       .partitionBy("load_partition")
       .mode("append")
       .parquet(base_path))

    partitions = [row["load_partition"] for row in df.select("load_partition").distinct().collect()]
    manifest_entry = {
        "loaded_at": datetime.now(timezone.utc).isoformat(),
        "row_count": df.count(),
        "partitions": sorted(partitions),
    }

    # Spark can append a manifest line the same way — write a tiny one-row
    # DataFrame in append mode rather than dropping down to a local file,
    # since the manifest itself may need to live on distributed storage too.
    manifest_path = f"{base_path}/_manifest.jsonl"
    spark.createDataFrame([(json.dumps(manifest_entry),)], ["line"]) \
         .write.mode("append").text(manifest_path)

    return manifest_entry

import pandas as pd
from pathlib import Path
import json
from datetime import datetime, timezone

def load_to_data_lake(df, base_path, partition_col="order_date"):
    df = df.copy()
    df["load_partition"] = pd.to_datetime(df[partition_col]).dt.strftime("%Y-%m-%d")

    output_path = Path(base_path)
    df.to_parquet(output_path, partition_cols=["load_partition"], engine="pyarrow")

    # A manifest records WHAT was loaded and WHEN. Without one, there's no
    # reliable way to later check whether a given batch already landed, or
    # to trace which run produced a specific file sitting on disk.
    manifest_entry = {
        "loaded_at": datetime.now(timezone.utc).isoformat(),
        "row_count": len(df),
        "partitions": sorted(df["load_partition"].unique().tolist()),
    }
    manifest_path = output_path / "_manifest.jsonl"
    with open(manifest_path, "a") as f:
        f.write(json.dumps(manifest_entry) + "\n")    # append-only log, one line per load run

    return manifest_entry

print(f"Loaded {result['row_count']} rows across partitions: {result['partitions']}")
Interview angle: The manifest is a small, hand-rolled version of what Delta Lake's transaction log or Iceberg's metadata layer do automatically — a durable record of what data exists and when it arrived, so a later job (or a human debugging an incident) can answer "did this batch actually load?" without re-scanning the entire lake. The pandas version writes from a single process; Spark's executors write their partitions in parallel — same partitioned-Parquet-plus-manifest shape, different execution model underneath it.
