# Databricks Connect v2: Intermediate

## Setting Up a Professional Dev Environment

Moving from a quick experiment with Databricks Connect to a team-ready development environment requires a bit more structure. A professional setup includes project configuration files, environment profiles, and a clear separation between local unit tests and cluster integration tests.

---

## Project Structure

A well-organized Databricks project using Connect looks like this:

```
my-databricks-project/
├── .databricks/             # Auto-generated by Databricks extension (gitignore)
├── databricks.yml           # Databricks Asset Bundle config
├── pyproject.toml           # Python package config and dependencies
├── src/
│   └── mypackage/
│       ├── __init__.py
│       ├── transformations.py
│       └── utils.py
├── tests/
│   ├── unit/
│   │   └── test_transformations.py   # Local unit tests (no cluster needed)
│   └── integration/
│       └── test_transformations_int.py  # Connect-based integration tests
├── notebooks/               # Notebooks that import from src/
│   └── exploratory.py       # Databricks notebook as .py file
└── .env                     # Local env vars (gitignored)
```

## databricks.yml — Asset Bundle Configuration

`databricks.yml` is the central configuration file for Databricks Asset Bundles (DABs). It defines your workspace settings, targets (environments), and resources (jobs, pipelines, etc.).

```yaml
# databricks.yml
bundle:
  name: my-analytics-project

workspace:
  host: https://your-workspace.azuredatabricks.net

# Define environment targets
targets:
  dev:
    mode: development
    default: true
    workspace:
      root_path: /Users/${workspace.current_user.userName}/.bundle/${bundle.name}/${bundle.target}
    variables:
      cluster_id: 0123-456789-dev-cluster   # Each dev uses their own cluster
      catalog: dev_catalog
      schema: ${workspace.current_user.userName}  # Personal schema per engineer

  staging:
    mode: staging
    workspace:
      root_path: /Shared/.bundle/${bundle.name}/${bundle.target}
    variables:
      catalog: staging_catalog
      schema: main

  prod:
    mode: production
    workspace:
      root_path: /Shared/.bundle/${bundle.name}/${bundle.target}
    variables:
      catalog: prod_catalog
      schema: main

resources:
  jobs:
    daily_etl:
      name: daily-etl-${bundle.target}
      tasks:
        - task_key: transform
          python_wheel_task:
            package_name: mypackage
            entry_point: run_etl
          new_cluster:
            spark_version: 14.3.x-scala2.12
            node_type_id: Standard_DS3_v2
            num_workers: 2
            spark_conf:
              spark.databricks.delta.preview.enabled: "true"
```

### Variable Substitution in Code

Your application code reads environment from variables, not hardcoded values:

```python
# src/mypackage/config.py
import os

CATALOG = os.environ.get("DATABRICKS_CATALOG", "dev_catalog")
SCHEMA = os.environ.get("DATABRICKS_SCHEMA", "dev")
CLUSTER_ID = os.environ.get("DATABRICKS_CLUSTER_ID", "")
```

## Environment Profiles with ~/.databrickscfg

For working with multiple workspaces or environments, use named profiles:

```ini
# ~/.databrickscfg

[DEFAULT]
host = https://prod-workspace.azuredatabricks.net
token = dapi_prod_token

[dev]
host = https://dev-workspace.azuredatabricks.net
token = dapi_dev_token

[staging]
host = https://staging-workspace.azuredatabricks.net
token = dapi_staging_token
```

Reference profiles in your code or CLI:

```bash
# Deploy to staging
databricks bundle deploy --target staging --profile staging

# Run integration tests against dev
DATABRICKS_CONFIG_PROFILE=dev pytest tests/integration/
```

```python
# In code, use specific profile
from databricks.connect import DatabricksSession
from databricks.sdk.config import Config

config = Config(profile="dev", cluster_id="0123-dev-cluster")
spark = DatabricksSession.builder.sdkConfig(config).getOrCreate()
```

## Databricks Asset Bundles (DABs) Integration with Connect

DABs and Connect complement each other in the development lifecycle:

- **Databricks Connect** is for **local development and testing** — running code from your IDE against a cluster
- **DABs** is for **deployment** — packaging code and deploying jobs, pipelines, and other resources to Databricks

They use the same `databricks.yml` file and the same authentication, so switching between "run locally via Connect" and "deploy as a job via DABs" is seamless.

### Typical Workflow

```bash
# Step 1: Develop locally with Connect (instant feedback loop)
python src/mypackage/transformations.py

# Step 2: Run unit tests locally (no cluster needed)
pytest tests/unit/

# Step 3: Run integration tests via Connect against dev cluster
DATABRICKS_CLUSTER_ID=0123-dev pytest tests/integration/

# Step 4: Deploy to dev via DABs and run as a job
databricks bundle deploy --target dev
databricks bundle run daily_etl --target dev

# Step 5: Deploy to staging/prod
databricks bundle deploy --target staging
```

## Debugging: Local Breakpoints with Remote Execution

This is the most powerful feature of Databricks Connect v2. You can set breakpoints in VS Code and step through your PySpark code line-by-line, even though the Spark computation runs remotely.

### How It Works

When you step through code in your debugger:
- Python-level code (defining transformations, calling `.filter()`, `.groupBy()`) executes locally
- When an **action** is triggered (`.show()`, `.collect()`, `.count()`), the logical plan is sent to the cluster for execution
- Results stream back to your local process
- You can inspect local variables, the DataFrame schema, and result data

### Setting Up VS Code Debugging

1. Install the **Databricks extension for VS Code** (marketplace: `databricks.databricks`)
2. The extension adds a Databricks panel in the sidebar for cluster selection
3. Create a launch configuration:

```json
// .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug PySpark (Databricks Connect)",
      "type": "debugpy",
      "request": "launch",
      "program": "${file}",
      "env": {
        "DATABRICKS_CONFIG_PROFILE": "dev",
        "DATABRICKS_CLUSTER_ID": "0123-456789-abcdefgh"
      },
      "console": "integratedTerminal"
    }
  ]
}
```

4. Set a breakpoint anywhere in your `.py` file
5. Press F5 to debug — breakpoints hit normally even as Spark runs on the remote cluster

### Practical Debugging Example

```python
# transformations.py
from databricks.connect import DatabricksSession

def clean_transactions(spark, input_table: str) -> None:
    df = spark.read.table(input_table)
    # Set breakpoint here — inspect df.schema in debugger
    
    filtered = df.filter("amount > 0 AND customer_id IS NOT NULL")
    # Set breakpoint here — filtered is still a lazy DataFrame (no execution yet)
    
    result = filtered.groupBy("region", "product_category") \
                     .agg({"amount": "sum", "customer_id": "count"})
    # Set breakpoint here — still lazy
    
    result.show(5)
    # <-- Execution happens here. After this line, you can inspect result in debugger

if __name__ == "__main__":
    spark = DatabricksSession.builder.getOrCreate()
    clean_transactions(spark, "main.raw.transactions")
```

### Inspecting DataFrames in the Debugger

In VS Code debug console, you can run expressions:

```python
# In debug console while paused at a breakpoint
df.printSchema()
df.count()          # triggers a job
df.take(3)          # returns 3 rows as Row objects
df.columns          # list of column names
```

## Using dbutils.fs from Connect

`dbutils` is available via the Databricks SDK:

```python
from databricks.connect import DatabricksSession
from databricks.sdk import WorkspaceClient

spark = DatabricksSession.builder.getOrCreate()

# Use WorkspaceClient for dbutils-like operations
w = WorkspaceClient()

# List files (equivalent to dbutils.fs.ls)
files = w.dbfs.list("dbfs:/mnt/raw/")
for f in files:
    print(f.path, f.file_size)

# Read a small file (equivalent to dbutils.fs.head)
content = w.dbfs.read("dbfs:/mnt/raw/config.json")

# Copy files
w.dbfs.copy("dbfs:/mnt/raw/file.csv", "dbfs:/mnt/staging/file.csv")
```

For secrets:
```python
from databricks.sdk import WorkspaceClient

w = WorkspaceClient()
secret = w.secrets.get_secret(scope="my-scope", key="db-password")
# Returns base64-encoded value
import base64
decoded = base64.b64decode(secret.value).decode("utf-8")
```

## Testing Strategy: Unit Tests vs Integration Tests

The key principle: **separate what needs a cluster from what doesn't**.

### Layer 1: Unit Tests (No Cluster Required)

Unit tests use local PySpark with a local SparkSession. They test transformation logic in isolation with small, mocked datasets. These run in milliseconds and require no authentication.

```python
# tests/unit/test_transformations.py
import pytest
from pyspark.sql import SparkSession
from pyspark.sql import Row
from mypackage.transformations import clean_transactions_df

@pytest.fixture(scope="session")
def local_spark():
    """Local SparkSession for unit tests — does NOT use Databricks Connect."""
    return SparkSession.builder \
        .appName("unit-tests") \
        .master("local[2]") \
        .getOrCreate()

def test_clean_transactions_removes_nulls(local_spark):
    data = [
        Row(customer_id="C1", amount=100.0, region="US"),
        Row(customer_id=None, amount=200.0, region="EU"),   # should be removed
        Row(customer_id="C3", amount=-50.0, region="US"),   # negative amount — removed
    ]
    df = local_spark.createDataFrame(data)
    result = clean_transactions_df(df)
    assert result.count() == 1
    assert result.collect()[0]["customer_id"] == "C1"

def test_clean_transactions_schema(local_spark):
    data = [Row(customer_id="C1", amount=100.0, region="US")]
    df = local_spark.createDataFrame(data)
    result = clean_transactions_df(df)
    assert "customer_id" in result.columns
    assert "amount" in result.columns
```

Your transformation functions should accept a DataFrame (not create the SparkSession), making them testable in isolation:

```python
# src/mypackage/transformations.py
from pyspark.sql import DataFrame
import pyspark.sql.functions as F

def clean_transactions_df(df: DataFrame) -> DataFrame:
    """Pure transformation — works with any SparkSession (local or Connect)."""
    return df.filter(
        F.col("customer_id").isNotNull() & (F.col("amount") > 0)
    )
```

### Layer 2: Integration Tests (Cluster Required via Connect)

Integration tests verify behavior against real Delta tables, real cluster compute, and real Unity Catalog permissions. They use Databricks Connect and run against a dev cluster.

```python
# tests/integration/test_transformations_int.py
import pytest
import os
from databricks.connect import DatabricksSession
from mypackage.transformations import clean_transactions_df

@pytest.fixture(scope="session")
def spark():
    """Databricks Connect SparkSession for integration tests."""
    return DatabricksSession.builder.getOrCreate()

@pytest.fixture(scope="session")
def test_catalog():
    return os.environ.get("TEST_CATALOG", "dev_catalog")

@pytest.fixture(scope="session")
def test_schema(spark):
    """Create an isolated test schema and clean up after."""
    catalog = os.environ.get("TEST_CATALOG", "dev_catalog")
    schema = f"test_{os.environ.get('USER', 'ci')}_{os.getpid()}"
    spark.sql(f"CREATE SCHEMA IF NOT EXISTS {catalog}.{schema}")
    yield f"{catalog}.{schema}"
    spark.sql(f"DROP SCHEMA IF EXISTS {catalog}.{schema} CASCADE")

def test_clean_transactions_against_real_data(spark, test_schema):
    # Write test data to a real Delta table
    data = [(1, "C1", 100.0, "US"), (2, None, 200.0, "EU"), (3, "C3", -10.0, "US")]
    df = spark.createDataFrame(data, ["id", "customer_id", "amount", "region"])
    df.write.format("delta").mode("overwrite").saveAsTable(f"{test_schema}.test_transactions")

    # Run the real function
    source_df = spark.read.table(f"{test_schema}.test_transactions")
    result = clean_transactions_df(source_df)
    
    assert result.count() == 1
    assert result.collect()[0]["customer_id"] == "C1"
```

### Running Tests

```bash
# Unit tests — fast, no cluster
pytest tests/unit/ -v

# Integration tests — requires running cluster
DATABRICKS_CLUSTER_ID=0123-dev \
DATABRICKS_CONFIG_PROFILE=dev \
TEST_CATALOG=dev_catalog \
pytest tests/integration/ -v -m integration

# Skip integration tests if no cluster available
pytest tests/ --ignore=tests/integration/
```

## Environment Isolation: Per-Engineer Dev Clusters

A common pain point in Databricks teams is shared clusters causing conflicts (one engineer's job kills another's session). The solution: each engineer gets their own dedicated dev cluster.

### Cluster Policies for Dev Clusters

Create a cluster policy in Databricks that enforces consistent, cost-controlled dev cluster configuration:

```json
{
  "cluster_type": {
    "type": "fixed",
    "value": "all-purpose"
  },
  "autotermination_minutes": {
    "type": "fixed",
    "value": 60,
    "hidden": false
  },
  "node_type_id": {
    "type": "allowlist",
    "values": ["Standard_DS3_v2", "Standard_DS4_v2"],
    "defaultValue": "Standard_DS3_v2"
  },
  "num_workers": {
    "type": "range",
    "minValue": 1,
    "maxValue": 4,
    "defaultValue": 2
  },
  "spark_version": {
    "type": "regex",
    "pattern": "14\\.[0-9]+\\.x-scala2\\.12",
    "defaultValue": "14.3.x-scala2.12"
  }
}
```

This enforces:
- Auto-termination after 60 minutes of inactivity (cost control)
- Limited node types (cost control)
- Max 4 workers (prevents runaway jobs)
- DBR 14.x (ensures Connect v2 compatibility)

### Personal Cluster Convention

Use naming conventions to identify clusters:
```
dev-<username>-connect
```

Each engineer creates their own cluster from the policy. Connect to it by setting `DATABRICKS_CLUSTER_ID` in your `.env`:

```bash
# .env (gitignored)
DATABRICKS_CONFIG_PROFILE=dev
DATABRICKS_CLUSTER_ID=0123-456789-yourcluster
TEST_CATALOG=dev_catalog
DATABRICKS_SCHEMA=your_username
```

Load `.env` automatically in your shell or via `python-dotenv`:

```python
# At top of conftest.py or main script
from dotenv import load_dotenv
load_dotenv()
```

## DataFrame Operations: What Works and What Behaves Differently

Some DataFrame operations have subtle behavior differences when using Connect vs. a full cluster.

### explain()

`df.explain()` works but the output is the logical plan — the physical plan may differ slightly from what you'd see in a notebook on the cluster, because optimization happens on the cluster side.

```python
# Works — shows the plan
df.filter("amount > 1000").explain(True)
```

### cache() and persist()

`cache()` and `persist()` are supported, but cached data is stored on the cluster's memory, not locally. This means:
- Caching still reduces re-computation on repeated actions
- But you cannot inspect cached partitions locally

```python
df.cache()           # Caches on cluster memory — works
df.persist()         # Works, same as cache
df.unpersist()       # Works
```

### count() Performance

Every action (including `count()`) sends the plan to the cluster and waits for a result. For large tables, this can be slow. Avoid calling `count()` frequently in development — use `df.limit(100).show()` for quick checks.

```python
# Slow for large tables — avoid in tight loops
df.count()

# Better for development checks
df.limit(5).show()
df.printSchema()     # No cluster call — schema is returned during plan analysis
```

### Collect and Memory

`collect()` brings ALL rows to your local machine. For large DataFrames, this can cause local memory issues. Use `limit()` or `toPandas()` with small result sets.

```python
# Dangerous for large DataFrames
rows = df.collect()  # Brings everything to local memory

# Safe alternatives
rows = df.limit(1000).collect()
pandas_df = df.limit(1000).toPandas()
```

## Complete Working Example

Here's a complete, realistic example of a data pipeline developed with Databricks Connect:

```python
# src/mypackage/pipeline.py
import os
import logging
from databricks.connect import DatabricksSession
from pyspark.sql import DataFrame, SparkSession
import pyspark.sql.functions as F
from pyspark.sql.types import DoubleType

logger = logging.getLogger(__name__)

# Pure transformation functions (testable without Connect)
def normalize_amounts(df: DataFrame) -> DataFrame:
    """Convert all amounts to USD (example transformation)."""
    return df.withColumn(
        "amount_usd",
        F.when(F.col("currency") == "EUR", F.col("amount") * 1.08)
         .when(F.col("currency") == "GBP", F.col("amount") * 1.25)
         .otherwise(F.col("amount"))
         .cast(DoubleType())
    )

def aggregate_by_region(df: DataFrame) -> DataFrame:
    """Aggregate transaction totals by region and date."""
    return df.groupBy("region", F.to_date("transaction_ts").alias("date")) \
             .agg(
                 F.sum("amount_usd").alias("total_amount_usd"),
                 F.count("*").alias("transaction_count"),
                 F.avg("amount_usd").alias("avg_amount_usd")
             )

# Orchestration function (requires SparkSession)
def run_pipeline(spark: SparkSession, source_table: str, target_table: str) -> None:
    logger.info(f"Reading from {source_table}")
    raw = spark.read.table(source_table)
    
    normalized = normalize_amounts(raw)
    aggregated = aggregate_by_region(normalized)
    
    logger.info(f"Writing to {target_table}")
    aggregated.write.format("delta").mode("overwrite").option("overwriteSchema", "true") \
              .saveAsTable(target_table)
    
    count = aggregated.count()
    logger.info(f"Pipeline complete. Wrote {count} rows to {target_table}")

# Entry point for local development via Connect
if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO)
    
    spark = DatabricksSession.builder.getOrCreate()
    
    catalog = os.environ.get("DATABRICKS_CATALOG", "dev_catalog")
    schema = os.environ.get("DATABRICKS_SCHEMA", "dev")
    
    run_pipeline(
        spark=spark,
        source_table=f"{catalog}.raw.transactions",
        target_table=f"{catalog}.{schema}.transactions_by_region"
    )
```

## Summary

- Use `databricks.yml` to define environment targets (dev/staging/prod) with per-environment variables
- DABs and Connect use the same config and auth — Connect for local dev, DABs for deployment
- VS Code debugger with breakpoints works with Connect — set breakpoints in `.py` files and debug PySpark locally
- Separate unit tests (local SparkSession, fast) from integration tests (Databricks Connect, real cluster)
- Give each engineer their own dev cluster with auto-termination via cluster policies
- Be aware of behavior differences: `cache()` stores on cluster, `collect()` can exhaust local memory, `count()` is a cluster round-trip
