## Scenario 1 (Junior): Choose a Primary Index for an Orders Table

**Context:**

You are designing a new `orders` table for an e-commerce data warehouse on Teradata. The table will hold approximately 500 million rows and will grow by roughly 2 million rows per day. Here is the proposed schema:

```sql
CREATE TABLE orders (
    order_id     INTEGER NOT NULL,
    customer_id  INTEGER NOT NULL,
    product_id   INTEGER NOT NULL,
    order_date   DATE NOT NULL,
    status       CHAR(2),
    amount       DECIMAL(15,2)
    -- PRIMARY INDEX ???
);
```

You know the following from the business:
- Queries most frequently filter by `order_id` (point lookups by order ID) or by `customer_id` (all orders for a customer).
- `order_id` is a surrogate key generated by a sequence — every value is unique.
- `customer_id` is not unique in this table — one customer can have thousands of orders. The top 100 corporate customers account for 40% of all order volume.
- The `orders` table will be joined to a `customer_dim` table that has `customer_id` as a **UPI**.

**Question:** Should you use `UNIQUE PRIMARY INDEX (order_id)` or `PRIMARY INDEX (customer_id)`? Justify your choice with reference to distribution, skew risk, and query performance.

<details>
<summary>✅ Solution</summary>

### Recommended Choice: `UNIQUE PRIMARY INDEX (order_id)`

**Justification:**

**1. Distribution and skew**

`order_id` is a sequence-generated surrogate key with guaranteed uniqueness and high cardinality (500M distinct values). The Teradata hash algorithm distributes these values uniformly across all AMPs, producing near-perfect balance.

`customer_id` as a NUPI is dangerous here. The top 100 corporate customers account for 40% of all rows. A single corporate `customer_id` could route millions of rows to one AMP — a textbook hot-key skew scenario. That AMP becomes the bottleneck for every full-table scan and every join.

**2. Point lookup performance**

The most frequent query type — lookup by `order_id` — becomes a **single-AMP retrieve** with a UPI:

```sql
-- With UPI(order_id): single-AMP retrieve — optimal
SELECT * FROM orders WHERE order_id = 9827341;
-- EXPLAIN: "We do a single-AMP retrieve from orders"
```

If `customer_id` were the PI, the same query would require either a full-table scan or a secondary index scan.

**3. Join to customer_dim**

`customer_dim` has `UNIQUE PRIMARY INDEX (customer_id)`. When you join `orders` (UPI on `order_id`) to `customer_dim` (UPI on `customer_id`) on `customer_id`, Teradata must redistribute rows. This is unavoidable regardless of whether `orders` has a PI on `customer_id` or `order_id`, because:
- `orders` NUPI on `customer_id` would co-locate with `customer_dim` UPI on `customer_id` — **but** the hot-key skew from corporate accounts makes this co-location harmful rather than helpful.
- `orders` UPI on `order_id` redistributes during the join, but the redistribution is done in parallel across all AMPs with even load.

**4. Secondary index for customer access pattern**

To support efficient "all orders for a customer" queries without using `customer_id` as the PI, add a Non-Unique Secondary Index (NUSI):

```sql
CREATE TABLE orders (
    order_id     INTEGER NOT NULL,
    customer_id  INTEGER NOT NULL,
    product_id   INTEGER NOT NULL,
    order_date   DATE NOT NULL,
    status       CHAR(2),
    amount       DECIMAL(15,2)
)
UNIQUE PRIMARY INDEX (order_id)
INDEX (customer_id);  -- NUSI for customer lookups
```

The NUSI creates a subtable that maps each `customer_id` to the AMPs and row IDs where that customer's orders live. Lookups by `customer_id` become a two-AMP-step operation (read subtable, then retrieve rows) rather than a full-table scan.

**Summary table:**

| Criterion | UPI(order_id) | NUPI(customer_id) |
|---|---|---|
| Even distribution? | Yes — sequence guarantees it | No — top 100 customers = 40% skew |
| Point lookup by order_id? | Single-AMP (best) | Full scan or secondary index |
| Skew risk? | None | High |
| Join to customer_dim? | Redistribution (parallel, even) | Co-located but skewed — net worse |
| Recommendation | **Choose this** | Avoid |

## Scenario 2 (Mid-Level): Diagnose Skew in a Large Join

**Context:**

A nightly ETL job calculates daily sales metrics and takes 3 hours — well past its 90-minute SLA. The query is:

```sql
INSERT INTO daily_sales_summary
SELECT
    c.region,
    c.segment,
    p.category,
    s.sale_date,
    SUM(s.amount)       AS total_sales,
    COUNT(DISTINCT s.customer_id) AS unique_customers
FROM sales_fact s
JOIN customer_dim c ON s.customer_id = c.customer_id
JOIN product_dim  p ON s.product_id  = p.product_id
WHERE s.sale_date = CURRENT_DATE - 1
GROUP BY c.region, c.segment, p.category, s.sale_date;
```

Table details:
- `sales_fact`: 8 billion rows, **NUPI on `customer_id`**, no partitioning.
- `customer_dim`: 50 million rows, **UPI on `customer_id`**.
- `product_dim`: 500,000 rows, **UPI on `product_id`**.

You run EXPLAIN and see: `"Skew: 71%"` on the spool generated for `sales_fact`. You also notice the join to `product_dim` is marked `"(duplicated on all AMPs)"`.

**Question:** Identify all root causes of the performance problem and describe the specific steps to fix each one.

<details>
<summary>✅ Solution</summary>

### Root Cause 1: 71% Skew on sales_fact

**Problem:** `sales_fact` has NUPI on `customer_id`. Some customers have vastly more transactions than others (e.g., a corporate account or a high-frequency trading customer). The AMP that holds those `customer_id` values processes 71% more rows than the average AMP — creating a severe bottleneck.

**Diagnosis:**

```sql
-- Confirm skew distribution
SELECT
    HASHAMP(HASHBUCKET(HASHROW(customer_id))) AS amp_num,
    COUNT(*) AS row_cnt
FROM sales_fact
WHERE sale_date = CURRENT_DATE - 1
GROUP BY amp_num
ORDER BY row_cnt DESC;

-- Find hot customer_ids
SELECT customer_id, COUNT(*) AS cnt
FROM sales_fact
WHERE sale_date = CURRENT_DATE - 1
GROUP BY customer_id
ORDER BY cnt DESC;
-- If top 5 customer_ids have >20% of rows, hot-key skew confirmed
```

**Fix A (immediate — no schema change):** Redistribute via a volatile table in the query:

```sql
CREATE VOLATILE TABLE sales_redistributed AS (
    SELECT
        s.*,
        (ROW_NUMBER() OVER (ORDER BY s.sale_id) MOD 128) AS bucket
    FROM sales_fact s
    WHERE s.sale_date = CURRENT_DATE - 1
) WITH DATA
PRIMARY INDEX (bucket)   -- 128 buckets → even spread across AMPs
ON COMMIT PRESERVE ROWS;

-- Now join from the redistributed table
INSERT INTO daily_sales_summary
SELECT c.region, c.segment, p.category, sr.sale_date,
       SUM(sr.amount), COUNT(DISTINCT sr.customer_id)
FROM   sales_redistributed sr
JOIN   customer_dim c ON sr.customer_id = c.customer_id
JOIN   product_dim  p ON sr.product_id  = p.product_id
GROUP BY 1, 2, 3, 4;
```

**Fix B (permanent — preferred):** Change `sales_fact` PI to `sale_id` (UPI, high cardinality) or add a PPI by `sale_date`:

```sql
-- Option: PPI by sale_date — partition elimination + contained per-partition skew
CREATE TABLE sales_fact_v2 AS sales_fact WITH NO DATA
PRIMARY INDEX (customer_id)
PARTITION BY RANGE_N(
    sale_date BETWEEN DATE '2020-01-01' AND DATE '2030-12-31'
    EACH INTERVAL '1' DAY
);

INSERT INTO sales_fact_v2 SELECT * FROM sales_fact;
-- Now WHERE sale_date = CURRENT_DATE - 1 eliminates 99.97% of partitions
```

---

### Root Cause 2: No Partition Elimination on sales_fact

**Problem:** `sales_fact` has 8 billion rows with no partitioning. Even though the query filters `WHERE sale_date = CURRENT_DATE - 1` (one day ≈ ~22 million rows), Teradata must scan **all 8 billion rows** across all AMPs because `sale_date` is not the PI and there is no PPI.

The PPI fix in Root Cause 1 Fix B also resolves this: with daily partitions, the query scans only 1/3,650 of the data.

---

### Root Cause 3: product_dim Broadcast (Duplication) Is Acceptable — But Verify

**Observation:** EXPLAIN shows `product_dim` is `"duplicated on all AMPs"` — this is a **broadcast join**. Teradata broadcasts small tables to all AMPs so the join can happen locally without redistributing `sales_fact`.

For 500,000 rows, this is typically fine and expected. However, verify that the broadcast size is within reason:

```sql
SELECT SUM(CurrentPerm)/1e6 AS size_mb
FROM DBC.TableSizeV
WHERE TableName = 'product_dim';
-- If < 500MB, broadcast is acceptable
-- If > 1GB, consider a join index or redistribution instead
```

---

### Root Cause 4: Stale Statistics

If statistics on `sales_fact(sale_date)` are out of date, the optimizer may not know how many rows `sale_date = CURRENT_DATE - 1` returns and could choose a suboptimal join strategy.

```sql
HELP STATISTICS sales_fact;
-- Check 'Last Collection Date' — if > 7 days old for a daily-loaded table, refresh

COLLECT STATISTICS
    COLUMN (sale_date),
    COLUMN (customer_id),
    COLUMN (PARTITION)    -- critical for PPI tables
ON sales_fact;
```

---

### Fix Summary

| Root Cause | Immediate Fix | Permanent Fix |
|---|---|---|
| Skew on customer_id (71%) | Redistribute to volatile table | Change PI to `sale_id` UPI or add PPI |
| No partition elimination | Filter to volatile table first | Add PPI by `sale_date` |
| Stale statistics | Refresh COLLECT STATISTICS | Automate daily stats collection |
| product_dim broadcast | Acceptable if <500MB | No action needed |

**Expected improvement after permanent fixes:** Query time should drop from 3 hours to under 20 minutes for a single day's data with PPI elimination and resolved skew.

## Scenario 3 (Senior): Design a Teradata to Snowflake Migration for a 100TB EDW

**Context:**

Your company runs a 100TB Teradata EDW (Teradata 6700 appliance) supporting:
- 1,800 tables across 12 business domains.
- 4,500 BTEQ and FastLoad/MultiLoad scripts orchestrated by Autosys.
- 200 Tableau dashboards and 50 MicroStrategy reports connected directly to Teradata.
- 120 active daily users (analysts) running ad-hoc SQL via BTEQ or SQL Assistant.
- SLAs: nightly ETL must complete by 05:00; morning reports must return in <30 seconds.
- Regulatory requirement: SOX-compliant audit trail for all financial tables; 7-year data retention.

**Business constraint:** Zero-downtime migration. The business cannot tolerate a scheduled outage longer than 2 hours for any single production table. The full migration must be complete within 12 months.

**Question:** Design the end-to-end migration architecture and sequencing plan. Address: wave sequencing, tooling for ETL translation, data synchronization strategy during the transition period, validation framework, and how you handle Teradata-specific features that have no Snowflake equivalent.

<details>
<summary>✅ Solution</summary>

### Migration Architecture Overview

```
┌─────────────────────────────────────────────────────────────────┐
│                     MIGRATION PHASES                            │
│                                                                 │

│  Phase 1 (Month 1-4): Wave 1 — Low-risk, high-value domains    │
│  Phase 2 (Month 4-8): Wave 2 — Core business domains           │
│  Phase 3 (Month 8-11): Wave 3 — Financial & regulated tables    │
│  Phase 4 (Month 11-12): Cutover, decommission, cleanup          │
```

### Phase 0: Assessment and Tooling Setup (Month 0–1)

**Inventory automation:**

```python
# Python script using teradatasql to catalog all tables
import teradatasql, pandas as pd

conn = teradatasql.connect(host=TD_HOST, user=TD_USER, password=TD_PWD)

tables_df = pd.read_sql("""
    SELECT
        t.DatabaseName,
        t.TableName,
        t.TableKind,
        SUM(s.CurrentPerm) / 1e9 AS size_gb,
        MAX(s.LastAccessTimeStamp) AS last_accessed,
        i.ColumnName AS primary_index_col,
        i.IndexType
    FROM DBC.TablesV t
    JOIN DBC.TableSizeV s
        ON t.DatabaseName = s.DatabaseName AND t.TableName = s.TableName
    JOIN DBC.IndicesV i
        ON t.DatabaseName = i.DatabaseName AND t.TableName = i.TableName
       AND i.IndexNumber = 1
    WHERE t.DatabaseName NOT IN ('DBC','SYSLIB','SYSSPATIAL','TDWM')
      AND t.TableKind = 'T'
    GROUP BY 1, 2, 3, 6, 7
    ORDER BY size_gb DESC
""", conn)

# Classify tables by size, access frequency, domain
tables_df['migration_wave'] = tables_df.apply(classify_wave, axis=1)
tables_df.to_csv('migration_inventory.csv', index=False)
```

**Tooling stack selected:**
- **Schema translation:** Snowflake Schema Conversion Tool (SCT) + custom Python for edge cases.
- **Data extraction:** Teradata Parallel Transporter (TPT) → Parquet files on S3.
- **Data loading:** Snowflake `COPY INTO` from S3 via Snowpipe for continuous sync.
- **ETL rewrite:** dbt (SQL models replace BTEQ) + Python (procedural BTEQ logic).
- **Orchestration:** Apache Airflow replaces Autosys.
- **Validation:** Great Expectations for data quality + custom row-count/checksum scripts.
- **BI layer:** Tableau re-pointed to Snowflake (connection swap, no report rewrites for most dashboards).

---

### Wave Sequencing Strategy

**Wave 1 — Reference & Lookup Tables (Month 1–4, ~5TB)**

Start with dimension tables and reference data: lowest risk, frequently read, rarely written, no complex dependencies.

- `product_dim`, `calendar_dim`, `geography_dim`, `organization_dim`
- No BTEQ ETL — mostly static loads from upstream systems
- Validate with exact row count + column-level checksum on all rows

**Wave 2 — Operational Domains (Month 4–8, ~60TB)**

Sales, Marketing, Supply Chain, HR. High query volume but less regulatory scrutiny.

- Migrate fact tables using dual-write during transition (see Data Sync section).
- Rewrite ETL scripts domain by domain with dbt.
- Run Tableau dashboards in parallel against both Teradata and Snowflake for 4 weeks before cutover.

**Wave 3 — Financial & Regulated Tables (Month 8–11, ~35TB)**

GL, AP/AR, payroll — SOX-regulated. Require audit sign-off before cutover.

- Enhanced validation: reconcile to source system (SAP) independently of both Teradata and Snowflake.
- Implement BigQuery row-level security equivalent in Snowflake via row access policies.
- Establish audit trail in Snowflake (see SOX section).

---

### Data Synchronization During Transition: Dual-Write Pattern

To achieve near-zero-downtime migration, implement dual-write during the transition period for each domain:

```
Upstream Source System
        │
        ├─── Existing ETL ──► Teradata (primary, serving production)
        │
        └─── New ETL (dbt) ──► Snowflake (shadow, validation only)
                                        │
                                 After 4-week validation
                                        │
                                        ▼
                             Flip: Snowflake becomes primary
                             Teradata kept read-only for 2 weeks
                             Then decommission that domain
```

For incremental sync (capturing changes after initial load):

```sql
-- CDC approach: use a high-watermark column on source
-- Initial load: full extract via TPT
-- Incremental: extract rows where updated_at > last_watermark

-- Airflow DAG task
def extract_incremental():
    last_wm = get_watermark('sales_fact')  # from control table
    tpt_command = f"""
    tbuild -f extract_incremental.tpt -v 'SelectStmt=SELECT * FROM sales_fact
        WHERE updated_at > CAST(''{last_wm}'' AS TIMESTAMP FORMAT ''YYYY-MM-DDBHH:MI:SS'')'
    """
    # Write to S3 as Parquet, then COPY INTO Snowflake
```

### ETL Translation Framework

**Category 1: Pure SQL BTEQ (60% of scripts) → dbt models**

```sql
-- Teradata BTEQ
INSERT INTO daily_sales_agg
SELECT region, sale_date, SUM(amount) AS total
FROM sales_fact
GROUP BY 1, 2;

-- dbt model (models/daily_sales_agg.sql)
{{ config(materialized='incremental', unique_key=['region', 'sale_date']) }}

SELECT region, sale_date, SUM(amount) AS total
FROM {{ source('raw', 'sales_fact') }}
{% if is_incremental() %}
WHERE sale_date > (SELECT MAX(sale_date) FROM {{ this }})
{% endif %}
GROUP BY 1, 2
```

**Category 2: FastLoad scripts → Snowflake COPY INTO via Airflow**

```python
# Airflow task replacing FastLoad
def load_to_snowflake(table_name, s3_path):
    snow_hook = SnowflakeHook(snowflake_conn_id='snowflake_prod')
    snow_hook.run(f"""
        COPY INTO {table_name}
        FROM @my_s3_stage/{s3_path}/
        FILE_FORMAT = (TYPE='PARQUET')
        MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
        PURGE = TRUE;
    """)
```

**Category 3: Procedural BTEQ (loops, conditional logic) → Python + Snowflake stored procedures**

```python
# Python replaces BTEQ procedural loops
def reconcile_accounts(run_date):
    snow = snowflake.connector.connect(...)
    cur = snow.cursor()
    
    cur.execute("SELECT DISTINCT region FROM account_dim")
    regions = [r[0] for r in cur.fetchall()]
    
    for region in regions:
        cur.execute(f"""
            CALL reconcile_region('{region}', '{run_date}')
        """)
        result = cur.fetchone()
        if result[0] != 'SUCCESS':
            raise Exception(f"Reconciliation failed for {region}: {result}")
```

### Teradata-Specific Feature Handling

| Feature | Frequency | Approach |
|---|---|---|
| `QUALIFY` window filter | High | Snowflake supports natively — no change |
| BTEQ `.IF / .GOTO` | Medium | Rewrite as Python control flow |
| `PERIOD` / temporal data | Low | Split to `valid_from` + `valid_to` DATE columns |
| Volatile tables | High | Replace with CTEs or Snowflake transient tables |
| FastLoad error tables | Medium | Use Snowflake COPY validation_mode + REJECTED_RECORD |
| COMPRESS column | All tables | Remove — Snowflake handles compression automatically |
| `SAMPLE n` rows | Medium | Rewrite as `SAMPLE (n ROWS)` in Snowflake |
| Teradata macros | Low | Rewrite as Snowflake stored procedures or dbt macros |
| `NORMALIZE` temporal | Low | Implement as window function logic |

### SOX Audit Trail in Snowflake

Teradata's journal tables provided SOX-required change history. In Snowflake:

```sql
-- Option 1: Snowflake Time Travel (90-day retention)
-- Query data as of any point in the last 90 days — satisfies short-term audit
SELECT * FROM financial_gl
AT (TIMESTAMP => '2024-12-31 23:59:59'::TIMESTAMP_NTZ);

-- Option 2: Audit log table (7-year retention)
CREATE TABLE audit.financial_gl_history (
    audit_id         NUMBER AUTOINCREMENT,
    operation        VARCHAR(10),   -- INSERT/UPDATE/DELETE
    changed_at       TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP(),
    changed_by       VARCHAR(100)   DEFAULT CURRENT_USER(),
    record_key       NUMBER,
    old_values       VARIANT,       -- JSON snapshot of pre-change row
    new_values       VARIANT        -- JSON snapshot of post-change row
);

-- Triggered via Snowflake stream + Airflow task
CREATE STREAM financial_gl_stream ON TABLE financial_gl;

-- Airflow task reads stream and writes to history table
```

### Validation Framework

```python
# Great Expectations suite for each migrated table
import great_expectations as ge

def validate_migration(table_name):
    # Row count check
    td_count  = get_td_count(table_name)
    sf_count  = get_sf_count(table_name)
    assert abs(td_count - sf_count) == 0, f"Row count mismatch: TD={td_count}, SF={sf_count}"
    
    # Column-level checksum (sampled for large tables)
    td_checksum = get_td_checksum(table_name)
    sf_checksum = get_sf_checksum(table_name)
    assert td_checksum == sf_checksum, "Checksum mismatch on sample"
    
    # Business metric reconciliation
    if table_name == 'sales_fact':
        td_total = get_td_total_revenue()
        sf_total = get_sf_total_revenue()
        assert abs(td_total - sf_total) / td_total < 0.0001, "Revenue reconciliation failed (>0.01% variance)"
```

### Cutover Playbook (2-Hour Window Per Domain)

```
T-00:00  Freeze writes to Teradata domain tables (set read-only via GRANT/REVOKE)
T-00:05  Run final incremental sync (TPT extract → Snowflake COPY INTO)
T-00:20  Run validation suite — row counts, checksums, business metrics
T-00:35  Flip Airflow DAGs from Teradata to Snowflake connections
T-00:40  Re-point Tableau/MicroStrategy data sources to Snowflake
T-00:50  Smoke test: run top 10 most critical queries on Snowflake; verify results
T-01:00  Declare cutover complete; open Snowflake to all users
T-01:00  Keep Teradata read-only for 2-week rollback window
T+14days Drop Teradata tables for this domain
```

**Risk mitigation:** If validation fails at T-00:35, the Teradata tables are still in read-only mode — flip Airflow back, investigate, and reschedule. No data is lost because Teradata was never written to during the sync window.
